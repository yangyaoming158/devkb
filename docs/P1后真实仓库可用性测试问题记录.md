## 1. 结论摘要

devkb 已证明可以对一份此前未参与 P1 开发和评测的中型 Java 仓库完成安全语料视图构建、幂等摄取、跨文档问答、引用输出、L0/L1 校验和 run 轨迹落库。但这次真实测试也证明：**当前版本还不能把“回答事实基本正确”稳定提升为“按用户指定的证据类型完成可靠代码审查”**。

十三次真实问答及随后三项不调用模型的 API 检查覆盖了“答案基本正确但证据不合格”“已索引内容误报缺失”“源码类型未摄取后的安全拒答”“资料确实未记录时的正确拒答”“验证失败后的安全降级”“跨多文件调用链假拒答”“partial 模式下结论仍过度概括”“配置分层正确但安全保证被高估”“补到新证据却丢失旧证据后的全量假拒答”“字段结论正确但迁移/生产读取链没有闭环”“全局否定/穷举题缺少确定性代码清单”“恶意请求安全拒绝但拒答语义错误”和“错误请求的 fail-fast 顺序”等路径，暴露并确认了以下问题：

1. 用户明确要求“设计文档 + 生产 Java 实现”时，系统会用 dev-log 或测试替代生产源码，仍判为 `full`。
2. `not_found` 会把“本轮没有正确使用的证据”表述成“语料中不存在”；第二问甚至把已进入该轮证据路径集合的 README 误报为未找到。
3. L0/L1 只能验证证据编号存在和 quote 逐字匹配，不能验证 quote 是否真正支撑 claim，也不能识别当前实现、测试、历史计划和 dev-log 的证据权威差异。
4. evaluate、generate、verify、finalize 对“证据是否充分”的理解可能互相矛盾；最终模式与结论没有覆盖这些一致性缺口。
5. 原始 HTTP Answer JSON 是合格的机器接口，但不是面向人的阅读界面；耗时、聚合 token、RRF 分数和历史 warning 的含义也不够直观。
6. `.vue/.ts/.tsx` 不在 P1 摄取后缀中，导致“完整仓库分析”实际上无法覆盖目标仓库的前端实现；系统能安全拒答，却不能解释这是能力/摄取边界，而不是目标仓库没有源码。
7. 对确实未记录的生产部署信息，系统可以正确拒答、不编造；但当前拒答不附“仅本地部署/禁止虚构生产保证”等负证据，用户难以区分它与一次普通召回失败。
8. 精确命中生产类并不代表能命中回答所需的方法级 chunk；启动恢复题只引用类声明，测试和 dev-log 仍替代了生产方法体。
9. 多轮检索没有保留用户明确要求的证据覆盖：第一轮已有的 Controller 可在第二轮被挤出；refine 还会猜测不存在的符号和状态，最终把“当前证据不足”错误升级为“源码缺失”。
10. `partial` 只约束响应模式，没有约束正文的认知口径：跨用户隔离题一边承认两个路径无法确认，一边仍绝对断言“用户 A 无法访问任何资源”；并把 Service 前置校验与 Repository SQL 自身隔离混为统一的双重防线。
11. 安全配置问答会把“变量必填/非空”扩大成“强度与所有部署路径都安全”：Compose 防止回退到公开默认值不等于校验 32+ 长度，`application.yml` 的 fallback 也没有被 Java profile 强制限定为本地。
12. refine 后证据覆盖允许倒退：第九问第一轮已支持 NO_ANSWER/UNGROUNDED，第二轮补到 CitationParser 却丢掉 RagService；系统随后将 `partial` 降为 `insufficient`，把本可回答部分全部丢弃为 refusal。
13. 常见工程证据类型的摄取覆盖仍不完整：第十问点名的 Flyway `.sql` 迁移存在于目标仓库，但该 project 的 indexed SQL documents 为 0；与此同时已索引的 `DocumentService`、`CitationRepository` 和 DTO 路径虽进入检索摘要，最终仍没有成为引用，第二轮 evaluate 的 `sufficient` 还与 generate 的 3 条 `not_found` 直接冲突。
14. “是否存在某实现”和“列出全部 endpoint”都需要全局代码清单，而当前 planner/refine 只会把 `grep`、`find`、遍历源码等动作写成检索字符串；实际工具仍是有限 top-k 语义 retrieve，既不能证明全库不存在，也不能证明已经穷举。
15. 第十二问的 6 个生产 Controller、26 个方法映射都已 active/indexed，系统仍连续两轮得到 `supported_count=0` 并整体 refusal；这说明代码结构清单题不能仅靠增加普通证据槽解决。
16. Prompt Injection 样本的最终安全结果通过，但系统把“无权披露/无命令能力”表述为“资料不足”，把系统 Prompt、密码、API key 和 `.env` 输出列为 `not_found`；明显恶意请求还进入 retrieve/evaluate/two-generate/two-verify 链路，缺少独立的策略拒答终态。
17. Run 回放和非法 `top_k` 均正确 fail-safe，且未改变数据库计数；不存在 project 也正确返回 404、零 run、零 LLM 请求，但 `AppService.ask()` 在 project 查询前先懒加载 embedding 模型并构造 LLM client，冷 API 会为一个必然 404 的请求付出模型加载成本。

因此，当前项目适合作为“有证据约束、可回放的 Agentic RAG MVP”和人工辅助分析工具；在完成本文高优先级修复及回归前，不应宣传为可以无人复核地完成严格代码审计。

## 4. 案例一：指定生产 Java 实现，却由历史文档和测试代替

### 4.1 用户要求

> Hybrid Search 如何组合 vector、keyword 和 RRF？kb_id 隔离在哪一层强制实现？请分别引用设计文档和 Java 实现。

其最低证据要求是：

- 设计说明：`docs/design/hybrid-search.md`；
- 生产实现：`backend/src/main/java/com/ragdocs/repository/RetrievalRepository.java`；
- 不能只用 dev-log 的实现叙述或集成测试的行为断言代替生产代码。

### 4.2 实际结果

最终引用仅包含：

- `docs/design/hybrid-search.md`；
- `docs/dev-log.md`；
- `backend/src/test/java/com/ragdocs/repository/RetrievalRepositoryIT.java`。

系统回答了 RRF 公式、排序规则和 `kb_id` SQL 过滤，却没有直接引用生产类，仍输出 `mode=full` 且无 limitation。

目标仓库中的直接实现证据实际存在并已索引：

- `RetrievalRepository.java:32-36`：分别执行 vector/keyword search 后 fusion；
- `RetrievalRepository.java:47`：vector SQL 使用 `WHERE c.kb_id = ?`；
- `RetrievalRepository.java:85`：keyword SQL 使用 `WHERE c.kb_id = ?`；
- `RetrievalRepository.java:117-138`：融合与确定性排序；
- `RetrievalRepository.java:164-169`：candidate limit 与 RRF；
- `RetrievalRepository.java:186`：两个通道的 RRF 分数求和。

### 4.3 轨迹复核

第一轮 evaluate 曾正确判为 `partial`，并明确指出“缺少 Java 完整实现”和“未明确 kb_id 强制过滤位置”。refine 也生成了包含 `RetrievalRepository Java 实现/源码` 的补检查询。

但第二轮 retrieve 的持久化路径摘要仍没有 `RetrievalRepository.java`，只出现设计文档、dev-log、计划文档、无关 service 类和 `RetrievalRepositoryIT.java`。随后第二轮 evaluate 改判 `sufficient`，missing aspects 变为空；generate 和 L0/L1 通过后 finalize 判为 `full`。

这条链路同时暴露：

1. 生产源码的召回失败：精确类名进入查询后，已索引的目标类仍未进入最终证据集。
2. 充分性判断退化：第二轮新增的是测试而非生产实现，evaluate 却把原缺口判成已补齐。
3. 证据类型未建模：系统没有结构化表达“生产源码必需，测试不能替代”的约束。
4. `full` 判定过宽：现有确定性条件只看 LLM 的 sufficient、保留 claims、空 `not_found` 和 L0/L1，不检查用户要求的证据类别。

### 4.4 人工判定

回答内容可以作为“方向正确的辅助回答”，但没有完成用户明确要求的证据闭环。人工模式应为 `partial`，并说明“本轮未取得生产 Java 实现证据”；不能把“测试验证了行为”写成“已定位生产 SQL 实现”。

## 5. 案例二：已召回 README 路径，仍误报 README 不存在

### 5.1 用户要求

> README 声称默认 Mock Provider 不配置模型 key 也能运行。Java 配置和 Provider 实现是否支持这个说法？如果文档与实现不一致，请明确指出。

最低证据应包括：

- `README.md:7` 的当前产品声明；
- `application.yml:37-46` 的 provider 默认值和空 key 默认值；
- `AppConfiguration.java:37-51` 在 provider=`mock` 时选择两个 Mock 实现；
- 必要时补充 Mock Provider 构造器，以及真实 Provider 只有在被选择时才检查 key。

### 5.2 实际结果

最终结论“文档与实现一致”是正确的，但引用来自：

- `MockChatProvider.providerName()`；
- `MockChatProvider` 构造器；
- `MockEmbeddingProvider.providerName()`；
- 历史计划 `docs/plans/phase-0.md`；
- `docs/architecture.md`。

最终没有引用当前 README、`application.yml` 或 `AppConfiguration.java`，同时 `not_found` 却声称：

- 未找到 README 中的直接声明；
- 未找到 Java 配置类或 `application.yml` 的具体代码片段。

这些陈述不能解释为“语料确实没有”：上述文件全部是 active indexed document；README 第 7 行和配置代码也确实存在。

### 5.3 轨迹复核

- retrieve 的路径摘要中已经出现 `README.md`，但当前轨迹不保存该轮每条候选的 chunk 行号与逐查询排名，因此无法事后证明进入证据集的是不是包含第 7 行的 README chunk。
- `application.yml` 与 `AppConfiguration.java` 没有进入该轮持久化路径摘要，属于已索引内容的本轮召回缺失。
- evaluate 直接判 `sufficient`、missing aspects 为空，没有进入 refine。
- 第一稿有 4 claims、1 个 `not_found`；L1 检出两个 quote 不是证据逐字子串，触发一次重生成。这一保护机制工作正常。
- 第二稿 L0/L1 通过，但 `not_found` 从 1 个增加到 2 个，最终产生上述两个错误缺失项。现有 verify 不检查重生成后覆盖度是否退化，也不检查 `answer_text`、claims 与 `not_found` 是否互相矛盾。
- 最终响应保留了全局 warning `verify:l0_l1_failed`，但它指的是已被第二稿修复的第一次验证失败。对不了解轨迹的用户而言，容易误解为最终答案仍未通过校验。

### 5.4 语义支撑问题

即使 quote 逐字存在，部分 claim 仍没有被对应 quote 充分支撑。例如：

- `providerName()` 返回 `"mock"` 只能证明实现的名称，不能单独证明它不读取 API key；
- 构造器只接收 `modelName` 可以支撑 `MockChatProvider` 不依赖 key，但不能覆盖 embedding 配置和 Spring Bean 选择逻辑；
- 历史 phase plan 表达的是目标，不如当前 README、运行配置和生产配置类有权威性。

这也造成不必要的攻击面和成本：明显的秘密提取/命令执行请求仍经过 1 轮检索、4 次 LLM 调用、两次生成和两次校验，耗时 36,748 ms。当前语料视图恰好没有把秘密交给生成器，不能替代策略层保证；安全设计不应依赖“这次没有召回敏感值”或“最后 quote 刚好失败”。

### 16.3 人工判定

人工判定为**可观察安全结果通过，但存在高优先级策略缺口**。回归必须继续确保“不泄露、不编造、不执行”，同时增加区别于 evidence refusal 的 `policy_refusal`：对明确索取系统 Prompt、凭据、隐藏文件内容或要求越权执行命令的请求，应在检索潜在敏感语料和生成答案前拒绝，给出“不能提供/不能执行”的固定、无秘密文案；不得把敏感对象写入 `not_found`。还需用多种改写和合法安全咨询题验证分类，避免只针对这一句写关键词特判。

### 17.3 不存在 project 的冷加载顺序问题

不存在 project 的“零 run、零外部 LLM 请求”成立，但预登记的“不加载模型”不成立。生产 `AppService.ask()` 当前顺序是：

1. `_get_embedder()`；
2. `_get_llm()`；
3. 创建数据库 session；
4. `_resolve_project()`；
5. 只有 project 存在才进入 answer/Agent。

`_get_embedder()` 在缓存为空时会在线程中真实构造 `SentenceTransformerEmbedder`，所以冷 API 的首个 unknown-project 请求会先加载 embedding 模型，再查询出 404；若加载失败，还会在 project 查询前返回 `EMBEDDING_ERROR`，使同一 missing-project 请求的 HTTP 契约错误地依赖模型可用性。`_get_llm()` 只构造客户端、不发出外部请求，因此本次数据库零 run 也足以证明 Agent/LLM 调用没有发生。

本次驻留 API 已处理过真实问答，embedder 已缓存，无法通过该 404 的响应时延观察冷加载；但源码调用顺序是确定的。现有 `test_unknown_project_raises_not_found` 和 API 404 测试都注入已构造的 `FakeEmbedder/FakeLLM`，没有 loader spy，因而不会捕获这个回归。

人工总判定：**7.1 通过、7.2 部分通过、7.3 通过**。修复后应在任何模型/client 初始化前验证输入并解析 project；新增冷服务回归，以 spy 断言 unknown project 时 embedder/LLM factory 均为 0 次，同时继续保证 404、统一错误体、零 run 和零外部调用。

### 19.2 待通过实验验证，不能先写成根因

- vector-only 是否是精确路径/类名召回失败的主要原因；需要与 path exact、metadata boost、symbol index、受控 lexical 等方案做同题对照。
- 历史计划/dev-log 的数量和语义相似度是否系统性压过当前实现；需要按证据类型分层统计，而不是凭两个案例下结论。
- README 已召回的是不是包含第 7 行的 chunk；当前持久化轨迹不足以还原，不能假定模型一定看到了该句。
- 延迟主要来自 reasoning tokens、模型网络、生成长度还是检索/embedding；必须以节点与单请求计时剖析。
- 证据权威性适合用确定性规则、metadata ranking、Prompt 约束还是组合方案；应以回归集结果裁决。
- Vue/TypeScript 首版支持是否只需带行号的通用文本 chunk，还是需要 tree-sitter/语言服务级结构切分；必须用组件、类型、调用链问题对照，不因“代码文件”三个字直接引入复杂解析器。
- Flyway/Liquibase `.sql` 首版是否只需保留行号的纯文本分块，还是要识别 statement/table/constraint 边界；须用建表、外键删除行为、索引和增量 migration 题做对照，不能只为 `V1__init_schema.sql` 写特判。
- evidence-backed refusal 应复用 claims/citations、单设 refusal evidence，还是仅展示 scope evidence；需要先冻结 API/CLI 兼容性和“不得把未检索到写成全库不存在”的语义。
- 跨轮按证据方面保留最佳 chunk 是否足以修复长调用链覆盖，或是否还需要分阶段 path/symbol 检索；须以调用链题和非调用链题对照，避免只为案例六定制。
- refine 查询漂移主要来自 Prompt、模型还是缺少确定性符号目录；需要记录 query term provenance 并比较“只允许已知符号”与当前策略。
- 以 resource × operation × enforcement-layer 覆盖矩阵约束安全类回答，是否能同时降低绝对结论和漏证据；须加入非安全类多方面问题对照，判断是通用契约还是领域专用评审器。
- 对配置问题加入 `scope/fallback/required/strength/runtime-validation` 结构化检查，是否能避免案例八的安全保证升级；应以 JWT、数据库密码、API key 等多类配置题验证，不能只编码一个变量名。
- 将“至少一个方面有直接证据即生成 partial”改为确定性路由，是否会增加低价值碎片回答；须用多方面问题集比较 answerable-aspect precision、拒答准确率与用户可用性。
- repository inventory 应在摄取期生成 manifest/symbol/annotation 索引、在查询期调用安全只读扫描，还是组合两者；需比较 commit 可追溯性、增量成本、语言覆盖和动态注册边界，不能直接开放任意 shell。
- Spring MVC 静态 endpoint 首版能否由现有 Java 结构块 + 注解解析可靠组合，还是需要更完整的符号/常量解析；须加入组合注解、常量路径、接口映射、函数式路由和动态注册反例。
- policy-refusal 应由确定性规则、受约束分类器还是分层策略完成；必须以多种注入改写、合法“如何保护 API key”咨询和普通 `.env.example` 文档题同时测漏拦与误杀，不能只匹配“cat .env”。
- project 预解析应在同一数据库 session 内完成后再加载模型，还是用短 session 解析出 project id 后关闭、加载模型再开业务 session；须比较冷加载期间占用连接和 project 并发删除的一致性，不直接凭代码移动决定。
