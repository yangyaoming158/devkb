# 《P1 Agentic RAG MVP 实现规格》

> 冻结日期：2026-07-16
> 前置 Gate：P0 已于 2026-07-16 复验通过
> 依赖：《范围冻结与架构决策》《P0实现规格》《Evaluation-v1》《ADR-0009》
> 当前阶段唯一实现依据；执行状态见《P1任务清单》。

## 1. 目标与范围

P1 把 P0 的固定 RAG 链路升级为一个**有界、可回放、会补检、会拒答的单 Agent 工作流**：

```text
问题
  → plan
  → retrieve（Vector + PostgreSQL FTS → RRF）
  → evaluate
      ├─ 证据充分 → generate
      ├─ 证据部分充分且已到上限 → generate partial
      ├─ 证据不足且仍可补检 → refine → retrieve → evaluate
      └─ 证据不足且已到上限 → deterministic refusal
  → verify（L0 + L1）
      ├─ 通过 → finalize
      └─ 不通过且未重生成 → generate → verify
  → finalize
```

P1 冻结交付：

1. Java 结构化解析；`.yml/.yaml/.properties` 按纯文本摄取；
2. PostgreSQL FTS，含 CJK 预分词与 camelCase/snake_case/数字标识符拆分；
3. Vector + FTS 双路召回、RRF 融合、HNSW；
4. LangGraph 单 Agent 有界工作流；
5. 充分回答、部分回答、拒答三态策略；
6. L0 引用存在性 + L1 引文原文匹配；
7. `agent_steps` / `tool_invocations` 轨迹和 CLI 回放；
8. Evaluation v1 harness、检索对照与 CI 回归门；
9. 最小 FastAPI：`POST /ask`、`GET /runs/{id}`、`GET /healthz`。

明确不做：Multi-Agent、MCP、LangFuse、reranker、PDF/OpenAPI/Python 解析、Redis、checkpoint、SSE/HTML 页面、鉴权/多用户、在线 NLI、冲突检测、增量索引、Dify/n8n、GraphRAG/Neo4j、云部署。以上能力仍受《路线图-v2》的后续 Gate 约束。

## 2. 继承与兼容性

- P0 的 `LLMClient`、`Embedder`、Repository/project_id 隔离和引用路径/行号契约继续保留。
- SQLAlchemy 查询构造仍只允许在 `src/devkb/repositories.py`；P1 不因模块增多而放宽 D7。
- P0 的 `ingest`、`ask`、`runs` CLI 保持可用；P1 只增命令和字段，不删除既有字段。
- P0 固定管道保留为 `fixed-rag` 对照 pipeline（其检索为 `vector-exact`），仅用于回归、评测和面试对照；默认交互 pipeline 切换为 `agentic` 后，二者必须共享底层 Repository、Embedder、LLMClient 和引用模型。
- LangGraph 可以有界使用 `langchain-core` 的消息/状态基础类型，但不得用 LangChain ChatModel、VectorStore 或 Retriever 替换现有接缝。
- P1 不启用 LangGraph checkpointer；一次 run 原子执行，失败写 `failed`，轨迹由业务表持久化。

## 3. 目录演进

在 P0 扁平结构上只做当前需求驱动的拆分：

```text
src/devkb/
├── api.py                     # FastAPI app 与 3 个路由；不放业务逻辑
├── service.py                 # CLI/API 共用应用服务与异常映射
├── agent/
│   ├── state.py               # AgentState、结构化输出模型、预算字段
│   ├── graph.py               # LangGraph 拓扑与确定性路由
│   ├── nodes.py               # plan/evaluate/refine/generate/verify/finalize
│   └── prompts.py             # 版本化 Prompt，禁止散落字符串
├── ingest/
│   ├── markdown.py            # P0 保持
│   ├── java.py                # tree-sitter Java 解析与结构化分块
│   └── pipeline.py            # 文件分派与公共摄取事务
├── retrieval.py               # vector/fts/RRF 编排与结果模型
├── evaluation.py              # Evaluation v1 harness
└── 其余 P0 模块保持
```

不得为 P2 预建 `mcp/`、`observability/`、`multi_agent/`、`graphrag/` 等目录。

## 4. 依赖与版本门禁

P1 允许新增且必须在 T11 基准任务中锁定兼容版本：

| 依赖 | 当前用途 | 边界 |
|---|---|---|
| `langgraph` + 必需的 `langchain-core` | 状态图与有界路由 | 不引入 LangChain 模型/向量库/检索器 |
| `fastapi` + ASGI server | 3 个最小 HTTP 接口 | 无 SSE、HTML、鉴权 |
| `tree-sitter` + Java grammar | Java 纯解析 | 永不编译或执行语料 |
| `jieba` | 摄取期与查询期 CJK token 化 | 输出必须确定性、可 golden 测试 |
| `httpx` | FastAPI 测试客户端 | 不新增任意 URL 抓取能力 |

版本选择先跑最小 spike，再更新 `uv.lock`；许可证和模型/API 条款结论记录为“已核查日期 + 来源 + 风险”，不做确定性法律判断。

P1 继续禁止：Redis、reranker/CrossEncoder、PyMuPDF、LlamaIndex、LangFuse SDK、MCP SDK、Neo4j driver、Dify/n8n 运行依赖。

## 5. 数据库迁移

P1 新增一个 Alembic revision（预计 `0002`，以实际 revision 链为准），在 P0 四表上扩展：

### 5.1 chunks 的检索字段

- `search_text TEXT NOT NULL DEFAULT ''`：应用层生成的规范化 token 流；包含标题路径、原文词、CJK 分词、标识符原词与拆分词。
- `search_tsv TSVECTOR`：由 `to_tsvector('simple', search_text)` 生成或在 Repository 中同步写入，具体方案以迁移 spike 可逆性为准。
- GIN 索引：`search_tsv`。
- HNSW 索引：`embedding vector_cosine_ops`，只覆盖非空 embedding；精确扫描模式仍保留用于评测基线。

迁移必须为现有 1370 个 P0 chunks 完成确定性 backfill；升级后不得要求用户删除并重摄 P0 数据。若数据库生成列方案无法安全回填，允许采用普通 `TSVECTOR` 列 + Repository 写入，但必须有一致性测试。

### 5.2 agent_steps

字段最小集：`id`、`project_id`、`run_id`、`seq`、`node`、`attempt`、`status`、`input_summary JSONB`、`output_summary JSONB`、`latency_ms`、`error`、`created_at`。

约束：FK 指向 project/run；`unique(run_id, seq)`；所有读取同时受 `project_id` 约束。

### 5.3 tool_invocations

字段最小集：`id`、`project_id`、`run_id`、`step_id`、`tool_name`、`arguments JSONB`、`result_summary JSONB`、`status`、`latency_ms`、`error`、`created_at`。

只存脱敏参数和摘要：不得写入 API key、整篇文档、完整 Prompt 或不必要的源码正文。

迁移验收：临时数据库执行 `upgrade head → downgrade 0001 → upgrade head`；生产验证只执行非破坏性的 `upgrade head`。

## 6. Java 与配置文件摄取

### 6.1 文件范围

- Markdown：`docs/**/*.md` + 根级 `README*.md`，继承 P0 范围。
- Java：`**/*.java`。
- 配置：`**/*.yml`、`**/*.yaml`、`**/*.properties`，按纯文本结构摄取；不解释或执行占位符。
- Markdown/TXT 行为保持 P0 兼容。

mini-mall 的 P1 生产/评测摄取**禁止直接把仓库根目录传给 `devkb ingest`**。核心 CLI 仍按目录扫描，不在 P1 为单一演示仓库加入隐式特判；精确范围由下述可复现语料视图落实。

### 6.2 可复现语料视图

P1 新增版本化 `corpora/mini-mall-p1.toml` 与标准库工具 `tools/build_corpus_view.py`。工具从只读源仓库复制候选文件到 `/tmp` 下的新目录，保持相对路径与原始字节，生成隐藏的 manifest（不参与摄取），记录源仓库 commit、每个 `rel_path`、sha256、类型和总数。

include：

- `docs/*.md`、`docs/**/*.md`、根级 `README*.md`；
- `**/*.java`；
- `**/*.yml`、`**/*.yaml`、`**/*.properties`。

exclude（include 后仍强制生效）：

- 任意隐藏目录或隐藏文件，包括 `.github/**`、`.playwright-mcp/**`；
- `**/node_modules/**`、`**/target/**`、`**/build/**`、`**/dist/**`；
- 任意层级的 `CLAUDE.md`、`AGENTS.md`、`TASKMASTER.md`；
- manifest 自身和非上述 include 类型。

2026-07-16 当前源快照的审计基线为 37 个 docs Markdown + 2 个根 README + 392 个 Java + 14 个配置 = 445 个文件。这个数字用于发现范围意外变化，不替代源 commit/hash manifest；源仓库发生合法变更时必须显式更新并复核 manifest，不能静默放宽规则。

视图构建后先断言三个指令文件、生成物目录和前端依赖均不在 manifest，再执行：

```text
devkb ingest <corpus-view-dir> --project mini-mall
```

禁止用 symlink 组装视图，避免 `Path.rglob` 跟随行为和源文件并发变化造成不可复现；禁止把复制后的 445 个语料文件提交进 devkb 仓库。

### 6.3 Java chunk

tree-sitter 至少识别：package/import 区、class/interface/enum/record、constructor、method、field group。每个 chunk 保留：

- 源文件相对路径和真实 `start_line/end_line`；
- `title_path`，例如 `com.example.OrderService > OrderService > createOrder`；
- 签名、紧邻注释/Javadoc 与完整或有界拆分后的正文；
- 原始 symbol 名写入 `search_text`，同时生成 camelCase/snake_case/数字边界拆分 token。

超长方法沿语句块或源行递归切分，但每个子 chunk 必须重复最小签名上下文，引用行号仍只指向真实源区间。语法错误文件允许 tree-sitter 容错解析；无法产出有效 chunk 时标记 `failed`，不得中断批次。

解析器不得启动 JVM、执行构建脚本、解析外部实体、访问网络或跟随语料中的命令。

## 7. FTS token 化

token 化是纯函数并在摄取期和查询期复用：

1. 保留原始可检索词；
2. snake_case 按下划线拆分并保留原词；
3. camelCase/PascalCase/字母数字边界拆分并保留原词；
4. 路径、类名、错误码、exchange/routing key 中的点、斜杠、短横线生成稳定 token；
5. CJK 片段用 jieba 分词；
6. 小写归一化用于匹配，但原文和引用不改写；
7. 空 token、超长 token 和重复 token 有确定性上限。

查询使用参数绑定构造 `websearch_to_tsquery`、`plainto_tsquery` 或等价安全表达式；禁止拼接用户输入到 SQL。具体函数由 T14 spike 冻结，必须覆盖中文、英文、Java 标识符、路径和 `40901` 这类数字 token。

## 8. Hybrid 检索与 RRF

每个查询或子查询执行：

1. Vector channel：HNSW top-N；评测模式可切精确扫描；
2. Lexical channel：FTS top-N，按 `ts_rank_cd` 或经 spike 冻结的排名；
3. 各 channel 内按 `chunk_id` 去重；
4. 使用纯函数 RRF 融合，默认 `k=60`；
5. 多子查询结果再次按同一证据 ID 去重并融合；
6. 返回最终 top-k，同时保留 `vector_rank`、`lexical_rank`、`fused_score` 和命中 query，供轨迹与评测解释。

默认上限：子查询 ≤3、每路候选 ≤50、最终证据 ≤12；全部经配置约束并设硬上限，用户不能绕过。

RRF 不混加余弦分数与 FTS 原始分数。无稳定评测收益时允许记录负结果，但 P1 默认路径仍须具备可工作的 Hybrid/RRF，并如实报告相对 P0 的变化。

## 9. LangGraph 状态、节点与预算

### 9.1 AgentState 最小字段

`run_id/project_id/question`、`plan`、`queries`、`retrieval_round`、`evidences`、`evaluation`、`answer_draft`、`verification`、`final_answer`、`llm_calls`、`token/cost/latency`、`warnings/errors`。

project_id 只由应用服务根据 slug 解析后注入，不能由 LLM 输出或工具参数覆盖。

### 9.2 LLM 调用点

遵守 D6，在线路径只有四类调用点：

| 调用点 | 最大次数 | 结构化输出失败后的默认 |
|---|---:|---|
| plan | 1 | 使用原问题作为唯一 query，意图=`knowledge_qa` |
| evaluate | 每轮 1 次，最多 2 次 | 保守判为 `insufficient` |
| refine | 最多 1 次 | 保留原 query，不再补检 |
| generate | 初次 + 重生成最多 2 次 | 第二次失败转确定性部分回答/拒答 |

单 run 发往 LLM 供应商的**总请求硬上限为 6，包含格式/传输重试**。每个逻辑调用点最多重问 1 次，且只有全局预算仍有余量时才能重问；重问同样计 request、token、成本和延迟。若重试消耗了原本留给 refine 或 regenerate 的预算，预算守卫必须裁掉后续可选调用并走冻结的 partial/refusal 默认路径。任何异常路径都不得形成无界循环。

### 9.3 确定性路由

LLM 只返回受 Pydantic 校验的信号；是否进入补检、生成、重生成或拒答由代码根据：轮次、预算、证据数量、结构化枚举和 L0/L1 结果决定。不得让 LLM 返回下一个节点名并直接跳转。

`recursion_limit` 仅作最后保险，不能代替业务计数器。

## 10. 回答、拒答与引用验证

P1 Answer 在 P0 字段上新增：

```text
run_id
mode: full | partial | refusal
claims[]: {text, evidence_ids[], quotes[]}
not_found[]
limitations[]
trace_summary
```

P0 的 `answer_text/citations/warnings/stats` 继续存在。

三态策略：

- `full`：证据评估为充分，生成的每个事实性 claim 至少绑定一个 evidence；
- `partial`：只有部分方面有证据，只回答可支持部分并明确列出 `not_found`；
- `refusal`：无证据或补检后仍不足，使用确定性模板说明缺什么，可展示最接近命中但不得把它包装为答案。

验证：

- L0：所有 `[E#]` 和 claim evidence_id 必须指向本次 evidence 集；
- L1：每个 quote 经空白/标点规范化后必须与对应 chunk 原文达到冻结阈值；阈值只能在 dev 集确定；
- 首次 L0/L1 失败：把机器可读错误反馈给 generate，最多重生成 1 次；
- 第二次仍失败：移除不通过的 claim，若剩余证据不足则确定性降级为 partial/refusal，并记录 warning；
- 只有 L0/L1 能触发重生成，evaluate 的“低信心”不能额外增加调用。

## 11. 轨迹与回放

每个节点无论成功、降级或失败均写一个 `agent_step`；检索等确定性能力每次调用写 `tool_invocation`。记录顺序、轮次、耗时、状态、有限参数、结果数量和错误类型，不记录 chain-of-thought。

`devkb runs show` 增加步骤摘要；新增 `devkb runs replay <run_id> --project <slug>` 以 Rich 表格展示：节点 → 判定 → 工具 → 证据数 → token/cost/latency → 降级原因。回放只读数据库，不重新调用模型或工具。

## 12. CLI 与 FastAPI

### 12.1 CLI

- `devkb ask` 默认使用 `agentic`；增加 `--pipeline fixed-rag|agentic` 供 P0/P1 问答链路对照，避免与检索评测 mode 混用。
- `devkb eval run --split dev|holdout --mode vector-exact|vector-hnsw|lexical|hybrid-rrf|agentic|all`；`all` 按前五种顺序运行，holdout 还需显式 `--confirm-holdout`。
- `devkb runs replay` 按项目隔离回放。
- `top_k` 必须校验为正数且不超过硬上限。

### 12.2 HTTP

- `POST /ask`：请求 `{project, question, top_k?}`，同步返回 P1 Answer；不做 SSE。
- `GET /runs/{run_id}?project=<slug>`：返回 run、steps、tool invocations 和 Answer。
- `GET /healthz`：检查进程、数据库连接和迁移版本；不触发模型下载或真实 LLM 调用。

默认只监听 `127.0.0.1`。P1 无鉴权，README 必须明确不得直接暴露公网。

Embedding 是同步 GPU 工作，API 路径必须移入线程并由进程内 semaphore 限制并发；不得阻塞事件循环。请求断开不取消已经写入数据库的 run，最终状态必须可查询。

## 13. 异常、安全与日志

- 应用服务统一把数据库、模型加载、LLM SDK 和解析异常映射为 `DevKbError`；CLI 不向普通用户输出原始 traceback，API 返回稳定错误码和可关联 error_id。
- 开发日志可保留 traceback 到 stderr，但 JSON stdout 和 HTTP body 不得混入日志。
- 输入上限：问题 ≤4000 字符、project slug/路径/run_id 严格校验、top_k 和候选池有硬上限。
- Prompt 中明确区分 developer instructions 与不可信 evidence；语料内指令只作为数据，不得改变工具/控制流。
- 轨迹、日志和 API 响应继续执行 secret 脱敏；不记录完整 Prompt/文档正文。
- P1 工具面全部只读；摄取仍是显式 CLI 管理操作，不由 Agent 自主调用。

## 14. 测试与 Evaluation v1

测试分层：

- 单元：Java 分块 golden、token 化、RRF、状态路由、预算、三态拒答、L0/L1、异常映射；
- 集成：迁移/backfill/GIN/HNSW、FTS、Hybrid、双项目隔离、steps/tools 落库；
- Graph：FakeLLM 脚本覆盖充分、补检、部分回答、拒答、重生成、预算熔断、工具失败；
- API：3 个端点、错误映射、project 隔离、并发边界；
- Evaluation：规则完全以《Evaluation-v1》为准。

CI 不下载真实模型、不调用 DeepSeek。CI 跑 `make ci` 和确定性 `make eval-ci`；真实 Qwen/DeepSeek 的 dev 与 holdout 只在本地阶段 Gate 运行并提交报告。

## 15. P1 验收标准

以下全部满足才可勾选 P1 完成：

1. 迁移可逆；P0 数据无损 backfill；GIN/HNSW 和两张轨迹表可用。
2. mini-mall 通过已审计的语料视图摄取 Markdown + Java + yml/yaml/properties，manifest 不含指令文件/生成物/依赖目录；二次运行零新增；抽查 Java 引用行号真实。
3. Hybrid/RRF 与 P0 vector 基线使用同一 dev 集完成受控对照，达到《Evaluation-v1》预冻结 Gate。
4. LangGraph 的 full/partial/refusal、补检和 L0/L1 重生成路径均有确定性测试，检索轮次 ≤2、供应商总请求（含重试）≤6。
5. 4 个 dev 不可答题达到拒答/边界回答 Gate，可答题误拒率达标。
6. `agent_steps/tool_invocations` 可按 run_id 回放；失败 run 也有完整终态和故障位置。
7. CLI、`POST /ask`、`GET /runs/{id}`、`GET /healthz` 通过集成测试；双项目数据不可越权读取。
8. 本地 `make ci && make eval-ci` 全绿，当前头提交 GitHub Actions 全绿。
9. P1 holdout 只运行一次并留档；不依据结果回改 Prompt、阈值、权重或标注。
10. README、架构图、状态图、评测报告和 5–8 分钟演示步骤与实际实现一致。

P1 通过只证明单 Agent Agentic workflow，不得对外宣称 Multi-Agent、MCP、LangFuse 或 GraphRAG 已实现。
