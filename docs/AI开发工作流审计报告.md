## 1. 总体结论

当前流程不是整体失控，而是“阶段治理较强、单任务收敛机制失效”。

项目已经具备不少成熟基础：阶段冻结、明确非目标、偏差裁决、真实仓库评测、Fake LLM/Embedder、完整 CI、跨项目隔离、holdout 纪律和详细开发日志。但这些规则主要约束“做什么”，没有充分约束“一个任务如何在一到两轮内做完”。

四到五轮返工的最主要原因不是简单的模型能力不足，而是：

1. 单任务过大，且实现前没有经过可持久化的任务合同、状态/数据流和测试不变量审查。T22、T23、T24 首次提交分别修改 11、16、11 个文件。
2. 测试数量很多，但关键对抗场景、变形不变量和组合性质是在审查发现缺陷后才补。绿色 CI 证明了已知用例通过，未证明语义契约完整。
3. 没有审查冻结和修复轮数规则。修复后 GPT 可以继续探索新组合，Claude 又继续局部补丁，导致修复引入新缺陷，未能在第二轮后返回设计阶段。

责任分布为：

- 工作流设计：首要责任。
- 执行者：存在过早声明完成、局部补丁替代结构分析、测试后补等问题。
- 审查者：样本中的发现大多真实、可复现且属于当前任务；没有证据表明 GPT 大量新增需求或审查整个仓库。但缺少审查冻结规则，使有效审查也无法自然结束。
- 项目复杂度：Agent 的跨轮状态、LLM 语义不确定性、自然语言约束解析和证据一致性，显著提高了组合缺陷概率。
- 任务定义：阶段规格并不模糊；问题是高层验收条件没有下沉成单任务的可执行不变量矩阵。

需要引入新 skills，但只建议两个组合型 skill：

- `project-preimplementation-gate`
- `project-scoped-review`

其余能力应放在简短的通用规则、任务模板、脚本或 CI 中，不应拆成十个 skill。

最推荐的改造方向是：一份共享 Task Packet、一次 GPT 前置计划审查、一个冻结的审查问题账本、最多一次普通修复、超过阈值立即回到设计或拆分任务。

## 2. 当前真实工作流

当前实际链路可还原为：

```text
用户指定当前清单任务
→ Claude 阅读阶段文档并直接调查/实现
→ 同时补测试
→ make ci + make eval-ci
→ 自审、勾选任务、写 dev-log、提交
→ GPT 审查完成后的 diff
→ 撤销勾选并 fix-forward
→ 补审查反例测试
→ GPT 构造新的组合场景复审
→ 再次 fix-forward
→ 重复，直至用户裁决或审查停止
→ 阶段末再做完整评测、holdout、远端 CI 和人工验收
```

失控点集中在“实现前”和“第一次审查后”：

```text
任务输入
  ↓
[缺少持久化任务合同、文件预算、可执行不变量]
  ↓
大跨度实现
  ↓
[测试主要证明已知场景]
  ↓
首次审查
  ↓
[没有一次性问题账本和第二轮审查边界]
  ↓
定向修复
  ↓
[修复没有结构退场条件，继续补例子]
  ↓
新组合缺陷
```

### T22：必需证据硬约束与权威性分层

原始目标：

- 把用户点名的证据类型、文件、符号变成 hard constraint；
- 确保不满足时不能输出 `full`；
- 区分生产源码、测试、设计文档等权威等级；
- 保持确定性和 fail-closed。

初始计划没有独立计划产物，只能从 `26777fd` 和事后日志反推。首次实现一次跨越 evidence schema、解析、路由、提示词、finalize、测试和文档。

返工链：

1. 一审发现 4 项：类型集合丢失点名身份、schema/evaluate 不完整、分类优先级、否定/缺失表达。
2. 二审再发现 4 项：`.java` 被句点切开、子串匹配、否定作用域、确定性覆盖与路由不一致。
3. 三审发现组合错误；日志明确记录上一轮“删英文句点”的修复治标并引入新问题。
4. 四审证明继续堆正则无法保障“漏解析必 fail-closed”，转向结构性方案。
5. 五审发现结构保证仍以整段 `produced` 判断，部分目标可静默消失，随后重写为约束跨度账本。
6. 六审发现“正文引用账本”和“claim 引用账本”不一致，禁引文档仍可出现在正文并得到 `full`。

证据见 `docs/dev-log.md` 的 T22 记录。

最终状态：

- T22.1/T22.3 经第六轮复审通过；
- T22.2 最后阻塞项修复后，由用户授权以自查复核代替第七轮独立审查；
- 因此功能已关闭，但流程证据不是完整的“独立终审通过”。

判断：

- 初始遗漏：约束身份、否定作用域、账本一致性和解析完备性。
- 修复引入：至少包括句点边界、跨句否定和多个局部解析问题。
- 审查范围漂移：未发现。
- 审查后新增需求：未发现；问题均可追溯到原任务“不得错误 full”的核心不变量。

### T23：not_found 四分类和历史事实校验

原始目标：

- 将缺口分成 `unsupported_or_not_ingested`、`corpus_index` 等明确类别；
- 所有 not_found 必须经过历史事实校验；
- 同一条只表达一个原因；
- 引用来源必须可追踪。

首次实现 `d586a33` 修改 16 个文件，新建约 444 行的 `not_found.py` 和约 434 行测试。

返工链：

1. 首次自审虽已发现 4 个问题，用户真实问题仍暴露“一条文本含两个目标、两个原因”，导致分类、basis 和 refs 自相矛盾。
2. 第一次修复引入通用文本 splitter。
3. 复审发现该 splitter：
   - 同原因多目标只保留第一个目标的 refs；
   - `涉及/或者/与此同时/参与` 被单字连接词误切。
4. 第二次修复引入中文屏蔽表。
5. 下一轮复审证明屏蔽表路线不可收敛：`或者` 被错误保留，`提及/与否/同时` 等自然语言无法穷举。
6. 最终改成“只有两个可识别目标之间才允许切分”的目标锚定方案。

证据见 `docs/dev-log.md` 的 T23 记录。

判断：

- 初始遗漏：混合目标/混合原因的测试矩阵。
- 修复引入：4 个后续问题均由 splitter/屏蔽表修复路径产生。
- 审查范围漂移：未发现。
- 新增需求：未发现。
- 最关键教训：自然语言处理规则不能靠不断扩展排除词表完成；应在计划阶段确定可证明的结构边界。

### T24：跨轮覆盖单调性和 partial 保留

原始目标：

- 前轮已经支持的方面不能因后轮 top-k 挤出而被误判为从未取得；
- 最终充分性不能只看最后一轮扁平证据；
- 至少有直接证据时应安全交付 partial；
- 淘汰和状态变化必须可追踪。

返工链记录在 `docs/P1.5任务清单.md` 的 T24 一至六审：

1. 一审 3 项：保留算法错误、历史支持冒充当前可交付、淘汰记录未持久化。
2. 二审 5 项：确定性轨被诊断轨饿死、LLM 自报回退、限定词身份不一致、轨迹截断、状态版本未递增。
3. 三审 2 个 P1 加 2 个注释漂移：任意路径交集被视为支持、方法或第二目标缺口被吸收。
4. 四审发现类型目标与符号目标不一致、长文本截断影响安全判断。
5. 五审发现句末标点被当成协调连接词，并有清单标号漂移。
6. 六审发现范围前缀被当成第二目标；原有 182,400 组合探针只证明“吸收时安全”，没有覆盖“等价变形不应改变吸收结果”。

最后一次提交 `734cd2d` 新增变形不变量，但 T24.1/T24.2 仍未勾选，等待第七轮独立复审。

判断：

- 初始问题既有状态模型和保留算法错误，也有“诊断信号是否具备裁决权”的架构问题。
- 多个后续问题由修复直接引入。
- 第三轮以后应停止继续补丁，返回状态/身份模型设计或拆分任务。
- 没有证据显示 GPT 离开当前任务边界；问题是流程允许同一个大任务无限探索，而不是审查意见本身无效。

三个最主要根因：

1. C + F：过大的跨层任务，在没有前置结构审查的情况下直接实现。
2. H + I：测试后补，缺少组合、变形和反例不变量。
3. N：没有修复退场条件，继续以局部规则修复结构性问题。

不同责任类型应明确区分：

- 执行模型质量：会出现局部推理和过早完成判断，但不是唯一或首要原因。
- 工作流：没有计划门禁、修复轮数、审查冻结，是首要系统性问题。
- 任务定义：规格详细，但任务粒度和可执行验收下沉不足。
- 测试：数量大，语义性质覆盖不足。
- 审查：缺乏收敛协议；目前没有证据表明审查者大量制造伪问题。
- 架构复杂度：状态账本、跨轮信号权威性和自然语言解析是高风险热点，应强制前置不变量审查。

## 8. 前置审查流程

### 任务合同

每个代码任务至少冻结：

- Task ID、base SHA；
- 目标和当前故障；
- 范围、非目标；
- 允许和禁止修改的模块；
- 最大核心文件数和预计 diff；
- 业务不变量；
- 权限和数据隔离要求；
- 状态转移和失败行为；
- 向后兼容要求；
- 验收标准；
- 预期测试；
- 未决问题。

合同通过后，普通需求不得在代码审查阶段新增。真正的新需求必须创建新合同或经用户批准修订合同并重做计划审查。

### 仓库事实调查

Claude 在这一阶段不得改代码，只回答：

- 入口在哪里；
- 当前调用链和数据流是什么；
- 哪些能力可以复用；
- 哪些模型字段和版本需要同步；
- 当前有哪些测试；
- 哪些文件只是上下文，哪些必须修改；
- 哪些假设尚无证据。

这可以防止 T22–T24 一开始就同时修改 schema、parser、nodes、prompts、trace 和 tests。

### 计划审查

GPT 只允许给出以下结果之一：

1. 计划通过；
2. 计划需要一次修订；
3. 任务必须拆分；
4. 证据不足，补充仓库调查。

GPT 不得在这里提出 P1.6/P2 架构升级。若发现现有规格矛盾，应输出“需要用户裁决”，不得自行选边。

### 测试和不变量审查

测试设计必须先于实现，至少覆盖：

- 正常路径；
- 边界和空输入；
- 非法状态；
- 重复请求；
- 越权；
- 外部服务失败；
- 部分成功；
- 重试；
- 序列化/结构化输出失败；
- 修复前的最小反例；
- 至少一条组合或变形不变量。

### 当前 Agent/RAG 特有风险

| 领域 | 当前已有能力 | 当前缺口或风险 | 应前置到任务合同的内容 |
|---|---|---|---|
| Agent 状态 | `state.py` 定义 running/succeeded/failed；`graph.py` 编码路由 | 没有统一状态转换表；DB 字段以字符串存储；ADR D6 明确无 checkpointer，进程崩溃可能留下 running run | 合法转换、终态、崩溃恢复、重复执行 |
| Tool Calling | 当前只有内部只读 retriever，调用可追踪；LLM 有 Pydantic schema、60 秒超时、SDK retry 关闭、最多一次结构重问 | 没有动态工具、风险等级、人工审批和写工具幂等设计；检索/DB 超时未形成统一门禁 | 工具 schema、后端校验、超时、风险级别、审批、幂等键、审计 |
| 数据一致性 | 文档按项目和路径唯一；摄取事务和 embedding 重试已有测试 | `/ask` 无请求幂等键；运行先落 running，再调用外部 LLM，进程崩溃可造成悬挂状态和重复费用 | 事务边界、部分成功、补偿、重复请求 |
| RAG | 项目隔离、文档状态过滤、L0/L1 引用存在性和逐字性较强 | 删除/重新索引的脏向量策略仍有限；API 当前依赖 loopback 而非用户权限；L1 不证明引用语义支持 | 删除一致性、权限过滤、引用语义、embedding 重试、真实使用检索证据 |
| LLM 不确定性 | 严格结构化输出、字段限制、失败降级和调用预算 | T22–T24 证明“JSON 合法但语义错误”是主要风险；policy refusal/prompt injection 仍在后续 T27 | 语义不变量、未知工具、拒答、解析失败、prompt injection |

当前项目不是完全缺少这些设计；问题在于它们分散在规格和代码中，没有作为每个相关任务的强制检查表。

## 9. 审查收敛机制

### 严重程度

| 等级 | 本项目定义 | 是否阻塞 |
|---|---|---|
| P0 | 不可逆数据损坏、跨项目/跨用户泄露、secret 暴露、任意代码执行、高风险操作绕过审批、核心数据不可恢复 | 始终阻塞，并可能升级为独立事故任务 |
| P1 | 当前核心流程错误、错误 full/refusal、非法状态、重复执行、幂等失败、事务部分成功、权限绕过、证据约束失效 | 始终阻塞 |
| P2 | 当前合同范围内的重要边界错误、异常不可恢复、关键测试缺失、合理输入不稳定、关键轨迹缺失 | 范围内阻塞；范围外进入新任务 |
| P3 | 命名、局部重复、未来扩展性、非阻塞文档优化、普通重构建议 | 不阻塞，进入 backlog |

### 收敛规则

1. Stage 4 计划通过后冻结普通需求。
2. 第一轮代码审查必须一次性列出所有已发现的阻塞项，每项有 issue ID、证据、严重程度和合同条款。
3. 历史问题不得记入当前审查；历史 P1/P2 进入 backlog。历史 P0 单独停止任务处理。
4. 第二轮审查只能检查：
   - 原 issue ID 是否关闭；
   - 修复是否直接引入新的 P0/P1。
5. 第二轮不得新增 P2/P3、未来优化或无关组合探索。
6. 正常任务最多一次定向修复。
7. 只有“一个局部、可证明、由修复直接引入的 P0/P1”才允许第二次修复，并需用户或计划门禁确认。
8. 如果第二轮出现两个及以上新 P1、相同不变量再次失败或需要扩大到计划外模块，立即停止补丁，返回 Stage 2/3。
9. 允许扩大范围的唯一条件是：仓库事实证明计划假设错误，用户批准合同修订，GPT 重新审查计划。
10. 验收通过条件：
    - P0=0、P1=0；
    - 当前合同内 P2=0；
    - exact HEAD 测试通过；
    - 没有计划外文件；
    - P3 已进入 backlog；
    - reviewer 明确输出 `PASS`。

对当前 T24，下一次审查应只验证 `734cd2d` 对六审 issue 的关闭情况和直接引入的 P0/P1，不应再开启第七轮全量属性探索。

## 10. 任务拆分规则

以下阈值是风险门禁，不是机械行数考核。

### 推荐任务大小

- 小任务：一个行为或不变量，最多 3 个核心源文件，附测试和必要文档。
- 中任务：一个子系统，最多 5 个核心源文件、8 个总文件，一组相关状态转换。
- 预计手写净增超过约 300 行时，必须说明为什么不能拆分。
- 测试文件不应被用来掩盖一个源代码任务实际跨越多个领域。

### 必须拆分的情形

- 超过 8 个非生成文件或 5 个核心源文件；
- 同时修改公共 API、数据库 schema 和 Agent 工作流；
- 同时修改 prompt/schema、解析器、状态机和持久化；
- 同时增加多个状态和外部调用；
- 同时包含新功能和重构；
- 存在两个以上独立回滚点；
- 无法用一句可观察结果描述验收；
- 预计需要多个独立提交才能分别验证。

按该规则，T22、T23、T24 首次实现都应在计划阶段拆分。

### Agent 功能拆分模板

1. 输出 schema 和纯合同验证；
2. 纯状态模型及合法转换；
3. 单节点行为；
4. 路由和跨轮编排；
5. 持久化、幂等和 trace；
6. API 序列化；
7. 真实评测和文档。

### RAG 功能拆分模板

1. 解析和 manifest；
2. chunk/vector/index 一致性；
3. 检索和权限过滤；
4. 重排、选择和预算；
5. 生成和引用；
6. 引用语义验证；
7. dev/holdout 评测。

`make ci` 包含 Ruff format/check、Pyright 和全部 pytest；CI 使用 PostgreSQL/pgvector 服务，基础门禁较强。

当前缺口是：

- `make eval-ci` 仍主要列出 P1 测试。T22/T23/T24 测试会因全量 pytest 被执行，但“P1.5 契约门”尚未显式进入 `eval-ci`。这与 T31 尚未完成一致，但在完成 T31 前，不能把当前 `make eval-ci` 绿色单独称为 P1.5 评测门通过。
- 无 diff scope、secret、debug、依赖锁和快照变更门禁。
- 无任务级测试选择与 exact-head 证据格式。
- Ruff 缓存曾出现本地绿色、远端 import 排序失败，应在最终验证关闭缓存。

### 建议命令

拟新增：

```text
make preflight
make verify-task
make verify-full
```

`preflight` 应执行：

```text
git status --short --branch
git diff --check
uv lock --check
uv run ruff check --no-cache src tests
uv run ruff format --check src tests
uv run pyright
```

并报告：

- 当前分支、base SHA、未提交改动；
- 当前任务是否与未完成任务重叠；
- 依赖或 lock 是否已变化；
- 是否适合开始任务。

`verify-task` 应接收 base SHA、Task Packet 和目标测试，执行：

- `git diff --check BASE_SHA...HEAD`；
- 检查 changed files 是否都在允许列表；
- 检查依赖、迁移、golden、snapshot、公共 API 变化是否已在合同批准；
- 只扫描新增行中的 `print`、`breakpoint`、`pdb`、TODO/FIXME、skip/xfail 和可疑宽泛异常；
- 运行合同中冻结的目标测试；
- 输出 head SHA 和命令结果。

Agent 类任务至少运行：

```text
uv run pytest -q \
  tests/unit/test_agent_state.py \
  tests/unit/test_agent_graph.py \
  tests/unit/test_agent_required_evidence.py \
  tests/unit/test_agent_aspects.py \
  tests/unit/test_agent_not_found.py \
  tests/integration/test_agent_service.py
```

RAG/数据一致性任务至少运行：

```text
uv run pytest -q \
  tests/integration/test_ingest.py \
  tests/integration/test_backfill.py \
  tests/integration/test_retrieval.py \
  tests/integration/test_isolation.py \
  tests/integration/test_answer_e2e.py
```

数据库变更任务至少运行：

```text
uv run pytest -q \
  tests/integration/test_migrations.py \
  tests/integration/test_repositories.py \
  tests/integration/test_isolation.py
```

`verify-full` 应执行：

```text
make ci
make eval-ci
```

并补充脚本门禁：

- tracked `.env`、私钥和常见 API key 模式；
- 未授权依赖/lock 变化；
- 未授权 migration/golden/snapshot 变化；
- debug 和测试降级扫描；
- Task Packet 和 exact-head 一致性。

### CI 阻塞条件

CI 应阻塞：

- format、lint、typecheck、任何测试失败；
- migration 和项目隔离测试失败；
- Agent 状态/契约测试失败；
- P1.5 eval gate 失败；
- 未经 Task Packet 批准的依赖、schema、golden 或 snapshot 修改；
- secret、debug、`if testing` 或新增测试跳过；
- changed files 超出允许范围。

暂不建议立即引入强制行覆盖率或 mutation testing。当前主要问题是语义不变量，而不是单纯未执行某行。可先使用 pytest 参数化、确定性组合矩阵和变形测试；Hypothesis 可在验证价值后再经依赖门禁引入。

未来 P1.6 出现动态工具时，再把 Tool Schema、后端二次校验、超时、风险级别、审批、幂等和审计测试设为强制门。

## 14. 最小落地方案

最多五项即可立即止损：

1. 修正 AGENTS，并增加“任务合同、大小门禁、最多一次普通修复、第二轮审查冻结”四条硬规则。
2. 新增一个合并式 `task-packet.md`，不创建多份计划和审查文件。
3. 所有中型/复杂任务在写代码前由 GPT 只审一次 Task Packet。
4. 首审使用 issue ledger；定向修复后只复核这些 issue 和直接新 P0/P1。
5. 复用现有 `make ci`，先补一个轻量 `verify-task` 检查计划外文件、diff、debug、测试降级和 exact-head。

这五项不要求修改业务架构，也不需要立即安装大量工具。

## 15. 完整落地方案

在最小方案稳定后：

1. 建立 `docs/development-workflow.md` 作为 Claude/GPT 共同事实源。
2. 创建两个组合型 workflow skills，分别负责前置门禁和 scoped review。
3. 把 Task Packet 与允许文件、base/head、测试证据连接到脚本。
4. 将 P1.5 确定性契约测试显式纳入 `eval-ci`。
5. 增加 migration、RAG 一致性、Agent 状态、未来 Tool Schema 的分类门禁。
6. 将 backlog 扩展为非阻塞问题的正式归档渠道。
7. 清理规则入口和阶段元数据漂移。
8. 记录下一批 10 个任务的流程指标：
   - 首次 diff 文件数；
   - 首审 P0/P1/P2 数；
   - 修复引入问题数；
   - 审查轮数；
   - 计划外文件数；
   - 是否在第二轮后回到设计。

不要把“所有任务零缺陷”作为目标；应以“普通任务平均修复次数小于 1，复杂任务在计划阶段拆分”为目标。

  - 扫描误报、CI 时间增长。
- 控制方式：
  - TODO/FIXME 等只检查新增行；
  - 快速检查与完整检查分开；
  - 首先复用现有工具。
- 验收标准：
  - 本地和 CI 使用同一完整入口；
  - 无缓存差异造成的本地/远端结果不一致；
  - 未批准的依赖、schema、golden 和范围变化可以自动阻断。

## 18. 最终判断

1. 当前工作流最应该先改哪三件事？

   - 用一份共享 Task Packet 在实现前冻结范围、文件预算、状态/异常流和测试不变量；
   - GPT 在代码前审计划，在代码后只审已冻结合同与 diff；
   - 第一轮形成 issue ledger，正常任务只允许一次定向修复，第二轮冻结审查范围。

2. 哪些问题不应继续依靠提示词，而应交给测试或 CI？

   - 状态转换、幂等、重复请求；
   - 项目隔离和越权；
   - migration、索引和删除一致性；
   - Tool Schema、参数校验、审批和超时；
   - 依赖/lock/schema/golden 非授权变化；
   - debug、secret、测试 skip/xfail、断言降低；
   - 允许文件和 exact-head；
   - required evidence、not_found、跨轮单调性等确定性不变量。

3. 最少需要哪些 skills？

   - `project-preimplementation-gate`
   - `project-scoped-review`

4. 哪些 skills 没必要创建？

   - 独立的 minimal-patch、diff-self-review、agent-invariant-review、bug-fix-protocol、definition-of-done、technical-debt-capture。它们应分别进入 AGENTS、Task Packet、两个组合 skill、CI 和 backlog。

5. 如何将平均返工次数控制在一轮以内？

   - 中型任务先审计划；
   - 超大任务先拆分；
   - 实现前冻结反例、组合和变形不变量；
   - 首审一次性列问题；
   - 修复只处理 issue ledger；
   - 第二轮不重新探索普通 P2/P3；
   - 出现多个新 P1 即停止补丁并回到设计。

6. 哪些情况下仍允许第二轮返工？

   - 只有一个局部、可证明、由第一次修复直接引入的 P0/P1；
   - 原计划和任务边界仍然成立；
   - 不需要修改新的核心模块；
   - 用户或计划门禁确认继续修复比重新设计风险更低。

7. 新流程会增加多少前期步骤，能减少哪些后期成本？

   普通代码任务实际只增加“一份 Task Packet + 一次计划审查”，预计约 15–30 分钟和 1,000–3,000 token；低风险任务更少。它将替代当前多轮重新加载上下文、反复撤销勾选、20 个修复提交、大量新增回归测试和四至七次独立审查。

建议用后续 10 个任务验证目标：普通任务平均修复次数小于 1，任何任务不超过两次修复，修复引入 P1 的比例显著下降。
