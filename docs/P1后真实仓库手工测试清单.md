- 人工判定：**失败（假拒答）**。四个明确要求的生产类全部 active/indexed：`RagService` 20 chunks、`RagSupport` 13、`CitationParser` 6、`RagConstants` 4。

- 摄取边界：目标仓库的 Flyway `V1__init_schema.sql` 确实存在，但 devkb 当前 `SUPPORTED_SUFFIXES` 不含 `.sql`；该 project 实测 indexed SQL documents=`0`。因此迁移证据不是普通低排名漏召回，而是 `unsupported_or_not_ingested`。相对地，`DocumentService`、`CitationRepository`、`CitationDto`、`MessageDto`、`RagService` 均为 active，分别有 16/6/2/2/20 个 chunks。
- 节点不一致：第一轮 retrieve 路径已有 `DocumentService.java`，第二轮已有 `CitationRepository.java`、`CitationDto.java` 和 `Citation.java`；第二轮 evaluate 仍判 `sufficient`、`missing_aspects=[]`，generate 随后却输出 3 条 `not_found`，其中再次声称未提供 `CitationRepository` 查询 SQL，同时把第一轮明确存在的 DTO 缺口静默丢掉。`DocumentService.delete` 本来也不应有“快照处理”调用——它只删 document，后果由迁移约束决定；正确做法是引用该方法说明没有显式 citation 变更，而不是寻找并不存在的专用处理代码。最终 `partial` 是安全兜底，但不能掩盖充分性判断、生成和证据选择之间的冲突。
- 精度问题：成功删除源文档后，原 chunk 会被级联删除，相关 citation 的 `chunk_id` 会被置空；当前 `CitationRepository` 的 `heading_path` 仅来自 live chunk 的 `LEFT JOIN`，此时会返回 `null`，不是回答中较含糊的“可能失效”。文件名和片段仍可显示，但 chunk/heading 定位能力确定性丢失。

## 9. 通用判定规则

- `full`：问题的每个明确方面和每个指定证据类型都已被直接证据覆盖，引用语义成立，`not_found` 为空。
- `partial`：只回答已有证据支持的部分，并准确说明本轮证据还缺什么；不能把未召回写成全库不存在。
- `refusal`：没有足够证据给出实质答案；不得编造。若已有范围/负证据，后续版本应说明为什么无法回答。
- 引用测试/计划/dev-log 可以补充行为和历史，但不能替代用户明确要求的生产实现。
- L0/L1 通过只代表 E# 存在和 quote 逐字匹配，不等于 claim 被语义支持；仍须人工抽查。
- 一个问题若同时包含太多生产类，系统诚实 `partial` 可以通过；缺证据却判 `full` 才是不通过。
