## 关键不变量

- **业务（PG-T302-03 修订：改为投影式，不再用"拼接=划分"的弱表述）**：`warning_details` 是唯一权威账本，另两个字段是它的**保序投影**。四条恒等式全部逐位成立（不是计数相等）：
  1. `[d.code for d in details] == state["warnings"]`（逐位等长同序）；
  2. `answer["warnings"] == [d.code for d in details if d.status == "active"]`；
  3. `answer["resolved_warnings"] == [d.code for d in details if d.status == "resolved"]`；
  4. `len(active) + len(resolved) == len(details)`（无条目落空、无条目两属）。
  > 为什么不能写成"`warnings + resolved_warnings` 是 `state["warnings"]` 的保序划分"：G2 实测顺序是 `[resolved, active, active]`，两张分类列表**直接拼接不可能还原全局顺序**；且"计数相等"发现不了分类内重排与重复 code 归错（G11 实测存在同组重复 code `generate:1:request_failed:LLMError` ×2）。投影式表述对这两类错误都是可判定的。
- **状态**：新增 `warning_records` 为只增（`operator.add`）通道，由**节点边界包装器唯一写入**；节点体一律不写它（结构上不可能与 `warnings` 漂移：记录是从同一次 `updates["warnings"]` 机械派生的，不是二次书写）。
- **权限/项目隔离**：不适用——`warnings.py` 不触 DB、不接受 project_id、不构造任何 sqlalchemy 查询（D7 不受影响）。
- **幂等/重试**：LLM 重问不推进 attempt（同一节点执行内）；节点重跑（第 2 轮 retrieve / 第 2 稿 generate+verify）推进 attempt。同一 run 内 `(node, attempt)` 唯一。

### 数据流

```text
节点 return {"warnings": [c1, c2], ...}
  └─ _attributed 包装器（节点边界，恒生效）
       attempt = state["node_history"].count(node) + 1      ← 执行前读，权威计数
       updates["warning_records"] = [WarningRecord(code=ci, node=node, attempt=attempt) ...]
  └─ LangGraph operator.add 归并 → state["warnings"] 与 state["warning_records"] 同序等长
终态 build_answer(state)
  └─ classify_warnings(codes=state["warnings"], records=state["warning_records"],
                       verify_runs=state["node_history"].count("verify"))
       ├─ 逐位配对（len 相等且 records[i].code == codes[i]）；否则 fail-closed 全 active + 归属留空
       ├─ R1 verify 取代 → resolved / superseded_by_regeneration
       ├─ R2 重问成功   → resolved / reask_succeeded
       └─ 其余          → active（fail-closed 默认）
  └─ warnings=active 投影 / resolved_warnings=resolved 投影 / warning_details=全量按序
```

### 冻结模型（PG-T302-02）

三个模型全部 `model_config = ConfigDict(frozen=True, extra="forbid", strict=True)`，与 `EliminationRecord`（`aspects.py:103-111`）同形：

```text
NodeName          = Literal["plan","retrieve","evaluate","refine","generate","verify",
                            "finalize","policy_refuse"]            # 与 graph.py:181-188 同源
WarningStatus     = Literal["active","resolved"]
WarningResolution = Literal["superseded_by_regeneration","reask_succeeded"]

WarningRecord   # 状态通道元素，由包装器机械构造
  code:    str      ← **plain strict str，不加 min_length/max_length**（见下「为什么 code 不得加约束」）
  node:    NodeName
  attempt: int      (ge=1)

WarningDetail   # Answer 层，U7 的构造入口
  code:       str      ← 同上，plain strict str
  node:       NodeName | None
  attempt:    int | None   (ge=1)
  status:     WarningStatus
  resolution: WarningResolution | None
  model_validator(mode="after") 强制三条交叉约束：
    ① status == "active"   ⇒ resolution is None
    ② status == "resolved" ⇒ resolution is not None
    ③ (node is None) == (attempt is None)          # 归属字段成对，不存在半归属
    ④ status == "resolved" ⇒ node is not None      # 无归属的条目不可能被任何规则判定
WarningLedger
  active:   tuple[str, ...]
  resolved: tuple[str, ...]
  details:  tuple[WarningDetail, ...]
```

非法组合（`active` 带 resolution、`resolved` 无 resolution、`attempt=0`、只给 node 不给 attempt、resolved 但归属为空、枚举外取值）**在类型层不可表达**，U7 对每条逐一断言 `ValidationError`。

**为什么 `code` 不得加任何长度/非空约束（PG-T302-02，第一轮修订直接引入的 P1）**：`code` 是**既有 `warnings` 通道的原文转载**，其合同就是 `list[str]`（`state.py:243`），从未有非空或长度上限。第一轮修订我给它加了 `min_length=1, max_length=500`，两处都会打断本来合法的执行：

1. **fail-closed 分支自相矛盾**：U4 要求空串恒 active，但 `WarningDetail(code="")` 会先抛 `ValidationError`，fail-closed 反而变成崩溃。
2. **合法 run 被中断（本轮实测）**：`GenerateOutput.not_found` 的单项上限就是 `ShortText` 的 500 字符（`state.py:59,145`），而 `not_found.py:691` 把该原文整条塞进 `:768-772` 的模板。实测脚本 `not_found=["库"×500]` 且同串出现在 `supported_aspects` 时——

   ```text
   GenerateOutput 合法解析 ✓ not_found[0] 长度 = 500
   → state["warnings"] 单条，长度 = 530（> 500）
   ```

   包装器构造 `WarningRecord` 时即抛异常，把一个**结构化输出完全合法**的 run 打成 failed。10 项时该 warning 可达约 5000 字符。

故两个模型的 `code` 一律沿用既有通道的 plain strict `str`：**本任务不给 warning 引入任何新的长度上限，也不做任何截断**（截断会丢信息，与"零 warning 丢失"直接冲突）。有界性由既有拓扑与 `MAX_*` 常量继承而来，不新增约束。

### 冻结规则（R1 / R2）

**R1（verify 取代）**——三项合取：

```text
record.node == "verify" and record.code == "verify:l0_l1_failed"
and record.attempt < verify_runs        # verify_runs = node_history.count("verify")
→ resolved / superseded_by_regeneration
```

**R2（重问成功）**——四项合取，**PG-T302-01 后由"词表"改为"规范语法 + 节点相符 + call_key 精确否决"**：

```text
① record.node ∈ {"plan","evaluate","refine","generate"}          # 只有这四个节点调 _structured_call
② record.code 完整匹配冻结正则（^…$ 锚定首尾，不用 in / endswith）：
   ^(?P<call_key>plan|refine|evaluate:[1-9][0-9]*|generate:[1-9][0-9]*)
    :(invalid_structured_output|request_failed:[A-Za-z_][A-Za-z0-9_]*)$
③ call_key 的节点前缀（":" 前第一段）== record.node                # generate:1 只能来自 generate 节点
④ 同一 (node, attempt) 组内不存在 f"{call_key}:default_applied"   # 按 call_key 精确匹配，非"任意 :default_applied"
→ resolved / reask_succeeded
```

四项缺一即 active。这四项对应 `_structured_call` 产出 code 的机器格式（`nodes.py:663/676/699/751` 的 f-string）与四个 call_key 取值（`plan` `:939`、`evaluate:{round}` `:1069`、`refine` `:1128`、`generate:{n}` `:1181`）。

**为什么必须收紧（PG-T302-01 的实测复现）**：原表述"后缀 `:invalid_structured_output` 或含 `:request_failed:`"既不约束节点也不约束语法，而 `finalize` 的多条 warning **逐字插值 LLM 自由文本**——`not_found.py:691` 把 `GenerateOutput.not_found` 的**原文**塞进 `:770` 的模板。本轮在 `826a4df` 上实测复现：

```text
脚本 [PLAN, EVAL_COLLIDE, GEN_COLLIDE]（evaluate 自报 supported_aspects 与 generate 自报
not_found 同为 "库存:request_failed:LLMTimeoutError"）
→ state["warnings"] == ['finalize: 前轮已支持方面被后轮报为缺失，已剔除（库存:request_failed:LLMTimeoutError）']
```

该条由 `finalize` 返回、组内无 `:default_applied`，**原 R2 会把它判成 resolved**，即把一条真实的终态 warning 藏进已解决桶——与 U4/验收标准"未识别 code 恒 active"直接冲突。收紧后它在①③两项上即被否决（node=finalize、无合法 call_key 前缀）。G8 用**这个脚本**做绑定负例。

`:budget_exhausted` 不入 R2：它在 `_structured_call` 里必然与 `:default_applied` 同组产生（`nodes.py:663` break 后落 `:751`），入不入表都是 active，不入表更贴合 fail-closed 默认（U11 锁定）。

### 状态流

- `warning_records` 只增不减，与 `warnings` 严格同序等长（包装器唯一写入点保证）。
- 分类**不写回状态**：`state["warnings"]` 与 `agent_steps` 的既有摘要一字不变，划分只发生在 Answer 序列化层。这样"全量账本"在轨迹侧、"时态划分"在应答侧，同一事实不存两份可写副本。
- `verify_runs` 取自 `node_history`，不取自记录本身——**第二稿通过时 verify 不发 warning**，用记录反推最大 attempt 会漏判（案例二/八恰好是这个形状），这是本设计的关键点。

### 异常与恢复流

- 节点抛异常：`_attributed` 不捕获、不产生记录；`_traced` 既有 failed step 行为不变。
- 绕过图直接调用节点方法（`tests/unit/test_agent_graph.py:1150,1780,2077,2667` 现有四处 `AgentNodes(...).finalize(state)`）：不经包装器 → 记录为空 → `classify_warnings` 走 fail-closed 分支（全 active、归属留空、零条目丢失）。这些既有用例断言的是 `result["warnings"]`（节点返回值），不经 `build_answer`，故行为不变。
- 无 warning 的 run：三个字段均为空列表。

### 风险和停止条件

- **如果需要计划外文件**：停止并回本门禁。特别是——若发现 `warnings` 收窄会破坏某条 P0/P1 兼容回归的**有冻结依据的**断言，不得就地放宽该断言，须停止并重新设计（备选方案：`warnings` 保持全量、另加 `active_warnings`，但该方案不满足"不得再把历史 warning 当作最终未通过展示"，故须用户裁决）。
- **如果规格与代码事实冲突**：停止，写入《P1.5任务清单》文末偏差记录等裁决，不自行改规格。
- **如果超过文件预算**：停止并请用户裁决 `size_exception`。
- **如果核心不变量无法证明**：若发现任一节点存在不写 `node_history` 的 return 分支（attempt 计数失去权威来源），停止并回设计门禁——不得改用外部可变计数器绕过。
