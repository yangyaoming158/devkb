# Task Packet：T31.2R-d 全局否定题不得以 `full` 交付且必带能力边界声明

> 来源：《P1.5任务清单》T31.2 条目 📋 规划行第 ②（用户 2026-08-07 裁决）。合并 `T312R2-G2`（e06 交付 `full`，预期 `partial_or_refusal`）与 `T312R2-G3`（`disclosure_present=False`，正文以肯定语气断言仓库级否定而无能力边界声明）。**执行顺序 R-c ✅ → R-d（本任务）→ R-e → R-f → 第三次 dev。**

## 任务目标

一个正文里带着否定断言的回答，**不能再以 `full` 终态交付**；它降到 `partial` 后自动获得两段确定性能力边界文案（静态摄取覆盖披露 + 已验证范围句），于是 `global_negation_honest` 的 `disclosure_present` 与 `mode_matches` 两项同时成立。

## 背景与当前问题

**G2 和 G3 不是两个缺陷，是一个根因的两个症状。**已落盘 08-07 报告里 e06 的实况：

```
mode: full   expected: [partial, refusal]   mode_matches: False
global_negation: {"ok": false, "disclosure_present": false, "mode_matches": false}
not_found_details: []      limitations: []
answer_text: 根据现有证据，该后端没有使用消息队列（如 Kafka/RabbitMQ）：……
            未出现 Kafka/RabbitMQ 等消息队列组件 [E4]。
```

根因链，逐环有仓库证据：

1. **词表漏词**。`_REPO_LEVEL_NEGATION`（`src/devkb/agent/not_found.py:150-163`）是 12 条封闭短语表：`不存在 / 并未存在 / 没有实现 / 未实现 / 无此 / 查无 / 没有该文件 / 无该文件 / 无相关实现 / 均未提供 / 从未提供 / 完全缺失`。e06 用的是「**没有使用**」和「**未出现**」——**一条都不在表里**。
2. 于是仓库级否定降级机制根本没触发，不产生任何 not_found 条目。
3. `finalize_consistency`（`src/devkb/agent/nodes.py:454-456`）的既有降级条件是 `mode == "full" and not_found`；`not_found` 为空 → **不降级**，mode 停在 `full`。
4. `full` 分支（`nodes.py:1494-1496`）**不追加**覆盖披露、也不追加已验证范围句——`nodes.py:1470-1472` 逐字写着「full 不附」；且 `:1507-1508` 把 `final_not_found` 与 `final_not_found_details` 在 `full` 时**强制置空**。
5. 结果：`disclosure_present=False`（评测侧判据 `eval_contract.py:1427-1429` 找 `COVERAGE_DISCLOSURE_MARK`）、`mode_matches=False`，`global_negation_honest` 判红。

**修第 1 环会把 2–5 环一并带好**——这就是 G2/G3 必须合成一个任务的机器化理由。

- **用户影响**：`global_negation_honest` 是 §5.1 第 6 条的硬键。当前 e06 让它红着，而红的原因不是判据太严，是系统真的交付了一句**在 P1.5 无从证明**的仓库级断言（P1.5 无 inventory，见《P1.5实现规格》§5）。

### 为什么不加词，而是换判定方向

`_REPO_LEVEL_NEGATION` 是**用来产生断言**的表：命中它就把某条缺口降级为 `unverifiable_assertion`，是「我判定这是仓库级断言」。这种表加得再长也**证不出穷尽**——T31.2R-b 正是因为这个把一个硬键降成了报告项。

本任务反过来用：宽表只用来**否决 `full`**。误报的代价是「本可以 `full` 的题变成 `partial`」——方向保守，**不产生任何虚假断言**；而漏报（表外措辞）由 U3 当场登记为已知边界，不假装拦住了。两者都不需要「这张表是穷尽的」这个证不出的前提。

### 数据流

`answer`（generate 产出的正文）→ `finalize_consistency` 第三条规则 → `mode` 由 `full` 降 `partial` → `nodes.py:1490-1493` 的 partial 分支追加覆盖披露与已验证范围句 → `:1507-1508` 保留 `final_not_found_details` → 评测侧 `disclosure_present` 与 `mode_matches` 同时成立。**没有新的外部输入、没有新的 LLM 调用、没有新的落盘路径。**

### 状态流

终态枚举不变（`full` / `partial` / `refusal` / `policy_refusal`）。新增的唯一转换是 `full → partial`，且经由既有的 `min(..., key=_MODE_RANK)`，与另外两条降级规则同源。**不新增任何 `refusal` 转换**，`policy_refusal` 完全不受影响（U6 锁）。

### 异常与恢复流

- `answer_text` 为空串 → `any(...)` 恒 False → 不降级、不抛异常（U4）。
- 已经是 `partial` / `refusal` / `policy_refusal` → 规则的第一个合取项即为假，短路（U5）。
- 本任务不引入任何持久化或外部调用，无恢复流。
