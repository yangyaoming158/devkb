# Task Packet：T26.1 partial 正文限定已验证范围

## 任务目标

终态为 `partial` 时，用户可见的正文尾部必带一条**确定性范围声明**，逐一列出本次回答实际交付的引用来源与仍未覆盖的方面条数；同时 generate Prompt 在 partial 模式下明确禁止对未检查对象作全称断言。可观察结果：复现案例七的输入下，终态正文不再以"用户 A 无法读取或删除用户 B 的任何资源"结尾于无限定状态，而是附带"本次已验证范围 = 3 个引用来源 + 另有 2 条未覆盖方面"的可核事实。

## 背景与当前问题

- **当前行为**：`finalize`（`src/devkb/agent/nodes.py:995-1174`）对 `partial` 正文不做任何范围限定——模型正文原样交付（只过 `apply_l0` 的越界标记检查）。`_limitations`（`src/devkb/agent/answer.py:43-69`）只给一句泛化的"仅回答了现有证据支持的部分，未覆盖方面见 not_found"，不说明"已验证的到底是哪些资源"。
- **复现证据**（本任务基线 `7cde67f` 上的只读探针，FakeLLM + 完整 `run_agent`，脚本见"仓库事实调查·探针"）：

  ```text
  MODE: partial
  ANSWER_TEXT: 用户 A 无法读取或删除用户 B 的任何资源 [E1]。KnowledgeBaseRepository 的查询均带
               owner_id 过滤 [E1]。所有关键 Repository 方法都包含 owner_id/user_id 过滤，
               Service 层也重复校验 [E2][E3]。
  NOT_FOUND:   ["DocumentRepository 的按 owner 读取方法：该文件是本次回答的引用来源之一…",
                "当前证据未覆盖 RagService.findConversation 的实现，无法确认会话删除是否强制 owner"]
  LIMITATIONS: ["仅回答了现有证据支持的部分，未覆盖方面见 not_found"]
  WARNINGS:    ["finalize: not_found 指向本次回答的引用来源，且含未经确定性核验的命题（…）"]
  CITED_PATHS: [KnowledgeBaseRepository.java, DocumentRepository.java, ConversationRepository.java]
  ```

  即：正文首句是全称断言（"任何资源"）、末句是统一双重防线的全称概括（"所有关键 Repository 方法都包含…Service 层也重复校验"），而 `not_found` 同时承认 `RagService.findConversation` 未确认。**零 warning 指向这个越界**（唯一那条来自 T25.1 的引用来源披露），用户也无从知道"已验证范围"就是那 3 个文件。这与《P1后真实仓库可用性测试问题记录》§10.3 末句的人工判定逐字一致。
- **用户影响**：安全类问题上，一句"无法读取或删除任何资源"会被直接当成结论采信；而系统自己在同一份回答里承认两条路径未确认。这是 RT-18（高）的核心形态。

### Prompt 触发条件（PG-01 修订）

前审实测：`prompts.py:152` 是 `mode_hint = "full" if evaluation.sufficiency == "sufficient" else "partial"`，而本任务的复现目标 I1（案例七）恰好走 `sufficiency == "sufficient"` → `requested_mode == "full"`。初稿把指令写成"`requested_mode` 为 partial 时生效"，**在目标复现上根本不触发**。

修订后的触发条件改为「**或**」关系，以模型自己的缺口自述为主开关（它与 `not_found` 字段同源，模型写它时必然知道）：

> 当你在 `not_found` 写入任何条目、或 `requested_mode` 为 `partial` 时，正文结论必须限定在**已引用证据实际覆盖的资源与操作**；对未检查的对象不得使用"任何/所有/全部/一切/均/都/一律"等全称表述下结论。

不改 `GenerateOutput` schema、不改调用点、不新增字段——只是 `GENERATE_SYSTEM` 的两句文字。U16 逐字锁定"`not_found`"这一支出现在指令里（防止修订被回退成只认 `requested_mode`）。

### 全称扫描合同（PG-02 冻结）

`universal_claim_hits(answer_text: str) -> tuple[str, ...]`：

- **闭合词表**（**有序**，扩充需新任务，不得在实现中临时加词）：
  `("任何", "所有", "全部", "一切", "每个", "各个", "均", "都", "一律", "无一", "毫无", "从不")`
- **匹配**：在 `normalize_for_l1(answer_text)`（`verification.py:50`，NFKC + 中文标点映射 + 去全部空白）上做**子串**判定。复用冻结规范化，不另建一套。
- **计数与去重**：按**词表项**去重，**不**按出现次数计数——"所有"出现 3 次仍只算 1 项。返回值是命中的词表项元组，**按词表声明顺序**排列（与 `PYTHONHASHSEED` 无关，可逐字复算）。
- **扫描对象**：**追加范围句之前**的正文。这是唯一真正的防线，且结构性成立——范围句尚未存在，自触发无从发生。U18 ① 是第二道保险，但只能约束范围句的**固定文案**：句中插值的 `rel_path` 来自语料，理论上可能含词表内的汉字（如 `docs/全部接口.md`），确定性代码管不住语料命名，把它纳入断言等于给判据加一条证不了的话（PG-02-R 收窄）。
- **warning 模板**（逐字冻结，`{n}` = 命中项数、`{words}` = 顿号连接的命中词、`{m}` = `len(not_found)`）：

  ```text
  finalize: partial 正文含 {n} 类全称表述（{words}），本次仍有 {m} 条未覆盖方面；两者论域关系未作判定
  ```

  末句是硬性诚实边界：确定性代码证不出全称断言的论域与 `not_found` 条目的论域重叠（需 L2/NLI，D9 与规格 §14 禁止在线），故只报共存、不报冲突。
- **触发条件**：`mode == "partial"` ∧ 命中非空 ∧ `not_found` 非空。三者缺一不发——尤其 `not_found` 为空时正文里的"均"不构成可披露的张力。

### 数据流

```text
finalize 局部作用域（全部已存在，无新状态）

  mode, _ = finalize_consistency(...)          # nodes.py:1159，只可能 full→partial
      │
      ├── mode == "refusal" ─► answer = _refusal_text(not_found)   （既有分支，不变）
      │
      └── mode == "partial"
              │
              ├─(1) hits = universal_claim_hits(answer)      ← 扫描**追加前**的正文
              │        └─ hits ∧ not_found ─► warnings += 全称披露（论域关系未作判定）
              │
              └─(2) answer = answer + verified_scope_note(cited_paths, len(not_found))
                          ▲                      ▲
      visible_citations ──┘                      └── not_found（T23 校准后）
        (nodes.py:1092，与 Answer citations 同源)     (nodes.py:1154)
```

(1) 必须早于 (2)：范围句一旦落进 `answer`，再扫描就会把它自己的措辞算成模型的全称断言。

范围句渲染（只含可证事实，措辞待前审确认）：

```text
（本次已验证范围：本回答的结论仅覆盖以下 3 个引用来源——A.java、B.java、C.java；

```

- 零引用时：`（本次已验证范围：本次未产生引用来源，本回答未取得可核验的引用支撑。）`
  **措辞约束（第二轮前审 PG-02-R）**：此处**不得**写成"未产生**任何**引用来源"——"任何"在闭合词表内，U12 覆盖引用数为 0 的输入，会与 U18 ① 直接冲突。范围句的固定文案对闭合词表零命中是硬约束，改词时须重扫全表。
- `not_found` 为空时（T23 剔空可达，见 `test_agent_graph.py:636` 的 I2）：省略末句，**不写"另有 0 条"**。
- 路径超过 3 条时沿用 `_render_refs` 的"前 3 条 + 等 N 条"口径。

### 状态流

`finalize` 内新增的唯一顺序约束：追加点在 `mode, consistency_warnings = finalize_consistency(...)`（`nodes.py:1159`）**之后**。理由——`finalize_consistency` 会把 `full` 降成 `partial`（`nodes.py:436-441`），在它之前追加就会给这类终态漏贴范围句。U10 单独承担这条顺序证明。

**PG-04 更正**：初稿的 U11 设想"被 `finalize_consistency` 降为 `refusal`"，该构造在当前仓库**不可达**——`nodes.py:420-446` 的两条赋值分支都只写 `"partial"`，`refusal` 的两个分支只追加 warning 不改 mode，`min(..., key=_MODE_RANK)` 因此只可能产生 `full → partial`。U11 改用真实 refusal 入口（`draft.claims` 全部 L1 失败 → `kept` 为空 → `mode = "refusal"`，与 `test_second_failure_with_all_claims_removed_refuses` 同形），断言终态正文 == `_refusal_text(...)` 原值、不含范围句。实现仍显式只在 `mode == "partial"` 时追加，**不依赖** refusal 分支重建正文这条掩盖关系（U3/U11 双向锁定）。

### 异常与恢复流

- `draft is None` / `generate_failed`：`answer` 可能为空串或冻结默认文案，范围句照常追加（U8）。不因异常路径跳过——判据要求覆盖**全部** partial 终态。
- `visible_citations` 为空：范围句走"未产生引用来源"分支（U4），不抛异常、不改判终态。
- 纯函数无 I/O、无异常路径；`universal_claim_hits` 对空串返回空元组。
