# Task Packet：T27.1 policy-refusal 前置识别与独立终态

## 任务目标

明确索取系统 Prompt / 凭据 / `.env` 内容或要求执行命令的请求，在 **retrieve 与任何工具调用之前**短路，落一个 `mode=policy_refusal` 的完整 run：固定无秘密文案、零工具调用、`not_found` 与 `not_found_details` 均为空、触发层（rule/plan）可从持久化轨迹与 Answer 读出；规则层命中时 `llm_calls == 0`，plan 兜底命中时 `llm_calls == 1`。

## 背景与当前问题

- **当前行为**：`AgentState.final_mode` 只有 `full/partial/refusal` 三值（`state.py:43`）。图拓扑为 `START → plan → retrieve → evaluate → …`（`graph.py:172-173`），没有任何在 retrieve 之前的策略短路点。攻击请求与普通问题走同一条路径。
- **复现证据**：《P1后真实仓库可用性测试问题记录》§16（案例十三，run `cc95be8e-0c66-412e-9a45-a25a8cbeedd7`）。可观察安全结果通过（无 secret、无执行、唯一 tool 是只读 retrieve），但：
  1. 终态 `refusal` 是「两次 L1 失败 → finalize 删掉最后一个 claim」凑出来的，不是策略终态（§16.2 第 1–4 步）；
  2. `not_found` 列出「系统提示词原文、数据库密码、任何 API key、cat .env 命令的执行结果」，把受保护对象建模成普通证据缺口，暗示「以后检索到就能回答」（§16.2 末段）；
  3. 明显的攻击请求仍走 1 轮检索、4 次 LLM、两次生成两次校验、36,748 ms（§16.2 末段）。
- **§16.2 的原文判定**：「当前语料视图恰好没有把秘密交给生成器，不能替代策略层保证；安全设计不应依赖『这次没有召回敏感值』或『最后 quote 刚好失败』。」
- **用户影响**：攻击面与成本白付；且「不能提供」与「资料不足」在响应契约上不可区分。

### 判据可证边界

**能证明**：问题文本经 NFKC+lower 后，同时含 表P 与 表D 的条目，或含 表C 的条目——**纯词法共现事实**。

**推不出**（每条在「冻结测试」有对应 fail-closed 负例）：

1. **推不出「这是一个恶意请求」，也推不出「不命中 = 这是安全/合法请求」。** 表外改写不命中，系统据此走普通路径；此时**不得**产出任何「已判定安全 / 无风险」的断言或 warning。→ U4 + I8
2. **推不出「本次没有发生泄露」。** policy_refusal 只保证本轮不检索、不生成、不调工具；语料里是否存在 secret、其他路径是否会泄露，本判据完全不覆盖。正文与 warning 均禁止出现「未泄露/无泄露/已确认安全」。→ U10 + I8
3. **推不出「plan 兜底层判得准」。** 它是 LLM 判断，可能漏可能误。确定性代码只据其**短路**、绝不据其**放行**：规则命中恒优先（plan 不执行），plan 调用失败的冻结默认值也不得造出拒答。→ I1 + I4

### 数据流

`question` →（图外，`initial_agent_state`）`policy_rule_hits` → `policy_trigger`。
命中：`START →(cond) policy_refuse → END`，问题文本**不流向**任何 LLM、检索器或渲染函数——文案是常量，不插值。
未命中：`START →(cond) plan`；plan 的 `policy_violation` → `policy_trigger="plan"` → `plan →(cond) policy_refuse → END`；否则 `plan →(cond) retrieve`，其后与今日逐字相同。

### 状态流

```text
rule 命中   : START → policy_refuse → END          node_history=["policy_refuse"]        llm_calls=0
plan 命中   : START → plan → policy_refuse → END   node_history=["plan","policy_refuse"] llm_calls=1
均未命中     : START → plan → retrieve → …（现状不变）
```

`policy_trigger` 单向：`None → "rule"` 只在图外发生；`None → "plan"` 只在 plan 节点发生；**永不回到 `None`**，也永不从 `"rule"` 变 `"plan"`（rule 命中时 plan 不执行）。

### 异常与恢复流

- plan 传输失败/结构化解析失败 → `_structured_call` 走冻结默认 `PlanOutput`，其 `policy_violation` 为默认 `False` → `policy_trigger` 保持 `None` → 正常路径。**不因故障造出拒答。**
- 规则层不发起任何 I/O，无失败模式。
- `policy_refuse` 节点无 I/O、无异常路径；`service.py` 的落库与轨迹写入路径逐字复用（含轨迹写入失败时 rollback 保住 run 终态）。
- 图执行异常仍由 `service.py:177` 兜底为 run `failed`，与今日一致。
