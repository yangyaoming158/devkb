# Task Packet：T31.2R-a agent 结构化调用点稳定取回 JSON，且重问不再饿死 generate

## 任务目标

四个结构化调用点（plan/evaluate/refine/generate）向供应商声明 JSON 输出模式，并把**空串响应**当作失败；单点重问在会挤掉 generate 预留时不再发生。

**可观察结果（三条都是确定性可验的事实，不含发生率承诺）**：①`json_mode=True` 的请求带 `response_format`、P0 对照路径的请求不带；②`content` 为空串/纯空白/`None` 三者均判为空响应；③非 generate 调用的重问在剩余预算不足以给 generate 留 1 次时不发生。背景实测（**只作留档，不作验收判据**）：同一 evaluate 提示上，不带 `response_format` 空 `content` 7/8，带上后 `ok` 31/32。

## 背景与当前问题

- **当前行为**：`src/devkb/llm.py:93` 只读 `choice.message.content`，且只在 `content is None` 时判空响应；空串 `""` 被当作正常返回，交给 `schema.model_validate_json("")` → `json_invalid` → `nodes.py:699` 记 `invalid_structured_output`。
- **复现证据（2026-08-05 实测，真实 `deepseek-v4-flash`）**：
  - **机制**：同一 evaluate 提示两次调用——第一次 `message.content` **len=0**、`message.reasoning_content` len=731 且内容是**合法 `EvaluateOutput` JSON**、`finish_reason="stop"`、`reasoning_tokens=268`；第二次 `content` len=441（合法 JSON）、`reasoning_content` len=485（中文思维链，**不是 JSON**，直接校验失败）。**模型答对了，是客户端读错了字段**；且回退读 `reasoning_content` 在正常情况下会读到思维链，**不是无条件安全的改法**。
  - **发生率（受控探针，同一提示 N 次并发）**：不带 `response_format` → `empty_content` **7/8**；带 `response_format={"type":"json_object"}` → 第一组 `ok` 7/8，第二组 N=24 **`ok` 24/24**（合计 **31/32**，零 `api_error`，证明 `deepseek-v4-flash` 支持该参数）。
  - **预算链**：`graph.py:65` `can_refine` 预留 `remaining_llm_requests >= 3`（refine + evaluate + generate 各 1 次），**该算术不含 D6 明写的「重问消耗全局预算」**。正常 plan(1)+evaluate(1)+refine(1)+evaluate(1)+generate(1)=5，余 1；每轮 evaluate 各多重问 1 次即 =6，`_can_generate`（`graph.py:70` 要求 `remaining >= 1`）为假 → finalize 无 draft → refusal。
  - **实证后果**：T31.2 首次 dev 运行中 c05 的 trace 节点序列为 `plan→retrieve→evaluate(degraded)→refine→retrieve→evaluate(degraded)→finalize`，**`generate` 一次未执行**，`llm_calls=6`；而第二轮 retrieve **确实召回了** `IngestionRecoveryRunner.java`(E1, 行 10-14)。c08 同型。
  - **影响面**：该次 20 题运行 `invalid_structured_output` **29 次**、`default_applied` 15 次、`coverage_mismatch` **20/20**、`full` **0 个**、必需证据命中 6/35。历史对照（同模型）：`p1-dev-agentic-20260719T230855` 21 题 0 次、`p1-holdout-20260721T223756` 10 题 1 次。**成因不作单一断言**（供应商侧行为随时间变化、P1.5 Prompt 变长都可能）。

### 数据流

供应商响应 → `content` 非空白校验 → `LLMResult` → `schema.model_validate_json` →（失败）warning + 预算判定 → 重问或冻结默认值。JSON 模式只改**请求**侧一个字段，不改响应处理形状。

### 状态流

不适用 + 原因：不新增状态、不改路由函数语义。`llm_calls` 的推进点与含义逐字不变。

### 异常与恢复流

- 供应商拒绝 `response_format`（本实测未出现，但须 fail-closed）：`openai.OpenAIError` 走既有 `LLMError` 映射，由调用点按既有 `request_failed` 路径处理，**不静默降级为无 JSON 模式重试**（那会隐藏供应商契约变化）。
- 空串/纯空白响应：抛既有 `LLMError("LLM 返回空响应")` → `nodes.py:676` 记 `{call_key}:request_failed:LLMError` → 既有重问/默认值路径。**注意这是行为变化**：今天该情形记 `invalid_structured_output`，改后记 `request_failed:LLMError`——两者都进 warnings 且都消耗预算，但**语义更准**（是没拿到响应，不是模型输出不合规）。该变化须在 packet 与 dev-log 显式留档，并由 U 层断言固定。

### 风险和停止条件

- **如果需要计划外文件**：停止上报（例如发现须改 `route_after_*` 或 `answer.py`）。
- **如果规格与代码事实冲突**：停止，写入清单偏差记录等裁决。
- **如果超过文件预算（8）**：停止上报。
- **如果核心不变量无法证明**：如实记录，不降低断言。
- **如果实测发现 JSON 模式改变了模型输出的语义质量**（不只是投递字段）：停止上报——那超出"读对字段"的范围，须重新裁决。
