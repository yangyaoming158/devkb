### 根因（运行后只读排查，**更正** T312-G3 首版定性）

c05/c08 的 refusal 不是 refusal 路由或覆盖判定写错，而是 `OpenAICompatLLM` 与 `deepseek-v4-flash` 的交互缺陷。链条逐环有实证：

1. `src/devkb/llm.py:93` 只读 `choice.message.content`，且只在 `content is None` 时判空；
2. 实测 `deepseek-v4-flash` **间歇性**把完整合法 JSON 写进 `message.reasoning_content`、让 `content` 为**空串**——同一 prompt 两次调用：第一次 `content len=0` / `reasoning_content len=731`（内容是合法 `EvaluateOutput` JSON）、`finish_reason=stop`、`reasoning_tokens=268`；第二次 `content len=441`（合法 JSON）/ `reasoning_content len=485`（中文思维链，**不是 JSON**，直接校验失败）。**故"content 空就回退读 reasoning_content"不是无条件安全的改法**：正常情况下那里是思维链；回退必须仍走同一严格 schema 校验（校验失败照旧记 `invalid_structured_output`），且需评估与 D8/m16 断言 3「响应不含 chain-of-thought」的关系。
3. 空串进 `schema.model_validate_json` → `json_invalid` → `nodes.py:699` 记 `invalid_structured_output` → 按 D6 重问 1 次 → 再失败即用冻结默认值（`sufficiency=insufficient`）；
4. **重问吃掉生成预算**：`graph.py:65` 的 `can_refine` 预留 `remaining_llm_requests >= 3`（refine + evaluate + generate 各 1 次），**该算术不含 D6 明写的「重问消耗全局预算」**。正常路径 plan(1)+evaluate(1)+refine(1)+evaluate(1)+generate(1)=5，余 1；每轮 evaluate 各多重问 1 次即 plan(1)+evaluate(2)+refine(1)+evaluate(2)=6，`_can_generate`（`:70` 要求 `remaining >= 1`）为假；
