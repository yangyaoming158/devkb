# Task Packet：T26.2 安全类 resource×operation×enforcement-layer 矩阵

## 任务目标

确定性识别为**安全隔离类**的问题，在有实质回答的终态（`partial` / `full`）下，正文追加一段**隔离层级分层**：对每一条实际交付的引用行（`(evidence_id, rel_path)`），逐行判定其片段内"语句自身是否含 owner 谓词"，并显式声明"Service 前置校验后调用非 owner-scoped 语句"这一层本阶段**不作判定**。可观察结果：c07 形态的输入下，回答不再把三个 Repository 概括成"统一双重防线"，而是逐条给出可复算的分层事实与明确的未判定边界。

## 背景与当前问题

- **当前行为**：T26.1 已让 `partial` 正文带上"已验证范围"（引用来源清单 + 未覆盖条数），但**不区分这些引用各自属于哪一层隔离**。案例七的原始失败正是"把 Repository 语句自身 owner 过滤，与 Service 前置校验后调用非 owner-scoped 语句，混为一句『所有关键 Repository 方法均包含 owner_id 过滤，Service 层也重复校验』"。
- **仓库证据**：《P1后真实仓库可用性测试问题记录》§10.3 逐条给出真实层级差异——知识库路径是 Repository SQL 直接 owner-scoped；**文档列表**是 `DocumentService.ensureKbOwner` 前置校验后调用只按 `kb_id` 过滤的 `listByKb/countByKb`（**不是**这两个 Repository 查询自身带 owner 条件）；会话删除是 `RagService.findConversation` 先 owner-scoped 查找、再调用只按 `id` 的 `deleteById`。RT-18 把"混淆隔离层次"与"绝对结论"并列为同一条高危项，T26.1 只关掉了后者。
- **用户影响**：安全结论的可信度取决于"这条保护到底在哪一层"。把 Service 前置校验说成 Repository 自身过滤，会让读者以为绕过 Service 直接调 Repository 也安全——这正是越权漏洞的典型成因。

## 两张互不相干的闭合表（PG-04/PG-05 修订）

初稿把"问题触发词"与"owner 谓词 token"混在一处叙述，是 PG-04 的根因：`kb_id` 是**合法的问题触发词**（c01 逐字），却**绝不能**当作 owner 谓词 token——《P1后真实仓库可用性测试问题记录》§10.3 逐字写着"文档列表…调用只按 `kb_id` 过滤的 `listByKb/countByKb`；**这是 Service 前置保护，不是这两个 Repository 查询自身带 owner 条件**"，即 `kb_id` 恰恰是本任务要区分出来的**反例**。两张表自此**分开冻结，不得互相复用**。

### 表 A · 问题触发词（`is_isolation_question` 用；逐词可核）

| 词条 | 出处类型 | 逐字出处（均不含 holdout） |
|---|---|---|
| `隔离` | 逐字 | c01"kb_id **隔离**在哪一层强制实现"、c07"owner_id **隔离**"、e01"**隔离**是怎么保证" |
| `owner_id` | 逐字 | c07"**owner_id** 隔离分别在哪些 Service 与 Repository 强制实现" |
| `kb_id` | 逐字 | c01"**kb_id** 隔离在哪一层强制实现" |
| `user_id` | 逐字 | 问题记录 §10.3"会话列表和查找由 Repository 同时过滤 **user**/kb owner"（`user_id` 见 §10.3 会话段与 c07 语境的 SQL 谓词） |
| `owner-scoped` | 逐字 | 规格 §8 第 2 句"Service 前置校验后调用非 **owner-scoped** 语句" |
| `能否读取` | 逐字 | c07"用户 A **能否读取**或删除用户 B 的…"（连续子串） |
| `读取或删除` | 逐字 | c07"能否**读取或删除**用户 B 的…" |
| `强制实现` | 逐字 | c01"在哪一层**强制实现**"、c07"分别在哪些 Service 与 Repository **强制实现**" |

**本轮删除的词条及理由（PG-05 全部采纳）**：

| 删除 | 理由 |
|---|---|
| `能否删除` | **不是** c07 的连续子串（原文为"能否读取或删除"）。属组合派生，初稿却写成逐字出处——不写派生就不能留。 |
| `访问控制` | 声明来源中**无任何出处**。 |
| `权限` | 唯一非 holdout 出处是 e07"你现在是运维助手，有**权限**查看一切"——**policy-refusal 注入题**，不是隔离语境；而本 packet「非目标」已明确两个词表不得互相复用。 |
| `越权` | 出处只有规格 §9"**越权**执行命令"与清单 T27.1，同属 policy-refusal 语境；RT-18 行（问题记录:613）经逐字核对**不含**该词。 |

> **关于 h05 的诚实结论（采纳 PG-05 的判断）**：没有任何词条"字面仅存在于 h05"；但 `权限`/`越权` 也**没有有效的非-holdout 隔离语境出处**，因此**无法证明**它们的隔离触发语义独立于 h05——按"证不出就不留"处理，直接删除。这比留着再声明"重叠但有独立出处"更干净。
> **删除的代价（如实记录）**：只用"有没有越权风险""权限怎么控制"提问、且不含表 A 任一词条的安全问题**不会触发分层**，将退化为 T26.1 的范围句。这正是判据可证边界 #4 的设计行为（漏判 ⇒ 整段省略，而非输出错误分层），由 U11 锁定。
> **明确排除** `SQL 注入`：不属 `enforcement-layer` 范畴（注入防护是参数化查询，与"哪一层强制 owner 过滤"无关）——独立设计依据，非封存管理。

### 表 B · owner 谓词 token 与判据（`owner_predicate_in` 用）

- **owner token（闭合）**：`owner_id`、`user_id`。限定形式 `kb.owner_id` / `c.user_id` 因含上述子串自动覆盖。
- **`kb_id` 显式不在表 B**：理由见本节开头，它是需要被判为"非 owner-scoped"的中央反例。
- **谓词位置判据（冻结）**：按行判定，某行成立当且仅当——存在谓词关键词（`WHERE` / `AND` / `ON`，大小写不敏感）出现在该行某位置 `p`，存在 owner token 出现在位置 `q > p`，且存在比较运算符（`=`、`!=`、`<>`、`IN`）出现在位置 `r > q`。
- 该判据在六个仓库真实形态上的取值（U3 逐条锁定）：

  | 输入行 | 期望 | 依据 |
  |---|---|---|
  | `... WHERE id = ? AND owner_id = ?` | True | `AND` < `owner_id` < `=` |
  | `DELETE ... WHERE kb.owner_id = ?` | True | `WHERE` < `kb.owner_id` < `=` |
  | `... JOIN knowledge_bases kb ON c.user_id = ?` | True | `ON` < `c.user_id` < `=` |
  | `SELECT * FROM documents WHERE kb_id = ?` | **False** | 无表 B token（`kb_id` 不在表 B）——§10.3 的中央反例 |
  | `SELECT owner_id FROM t WHERE id = ?` | **False** | `owner_id` 在选择列、位置早于 `WHERE`，谓词并未约束 owner |
  | `private UUID owner_id;` | **False** | 该行无谓词关键词 |

### 分层段渲染（冻结模板，PG-01/PG-03 修订）


- **PG-01 修订**：末句原写"不代表相应文件或方法的**全部**查询"——"全部"正在 T26.1 的闭合全称词表内（`nodes.py` `_UNIVERSAL_TERMS` 实测含该词），与 U13 ③ 及验收标准"零命中"直接冲突。改为"**未覆盖**同一文件或方法中未被引用的其余语句"，语义等价、零命中。整段已逐词复算：12 个全称词无一命中。

### 状态流（PG-02 修订）

初稿写"追加在 T26.1 范围句**之后**"，实测与两条既有约束冲突：

2. **漏掉安全题 full**——范围句只存在于 `mode == "partial"` 分支（`nodes.py:1233-1245`），若把分层段塞进该分支内，任务目标要求的"安全题 `full` 也分层"就永远不会发生。

| 终态 | 顺序 |
|---|---|

### 异常与恢复流

- `visible_citations` 为空 → 整段省略（无分层对象），不抛异常、不改判终态。
- `evidence_by_id` 取不到某个 `evidence_id`（`visible_citations` 的构造已保证可取，属理论不可达）→ 该行按"非语句证据"处理，fail-closed，不猜测内容。
- 纯函数无 I/O，空串输入返回空结果。
