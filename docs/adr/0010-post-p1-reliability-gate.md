# ADR-0010：P1 后真实仓库可靠性 Gate（G1.5）与工具调用能力增量

- 状态：**已接受**（2026-07-23，用户批准 §4 可投递线重排与 §2/§3 的 P1.5/P1.6 切分线；2026-07-23 起草）。
- 依据：`docs/P1后真实仓库可用性测试问题记录.md`（RT-01～RT-23）、`docs/P1后真实仓库手工测试清单.md`、ADR-0009、ADR-0006（D6）
- 影响范围：在 ADR-0009 的可投递线中新增 G1.5 与 P1.6，并重排交付次序；**P0/P1 验收结论不变，D1–D11 现阶段行为边界不变**。

## 编号审计

`docs/adr/` 现存至 `0009`，《范围冻结与架构决策》§七登记至 `0009`。`0010` 未落文件、未登记、未预留，是下一个可用编号。

## 背景

P1 已按冻结规格 10/10 验收并正式关闭（`docs/P1任务清单.md`）。验收后，用户把 devkb 指向一份此前未参与 P1 dev/holdout 的陌生 Java 仓库（`rag知识库项目 @9bb79cd`），执行 13 次真实 DeepSeek 问答 + 3 项不调用模型的 API 检查，归档为 RT-01～RT-23。

结论不是小瑕疵，而是核心可靠性缺口：系统能安全问答、回放、正确拒答真正无资料的问题，但**做不到稳定的指定证据约束、跨轮证据保持、准确 `not_found`、全局穷举/否定证明与严格代码审查**；且缺少独立的 policy-refusal 终态，unknown project 的 fail-fast 顺序有瑕疵。

这些缺口不能靠直接进入 ADR-0009 的 P2 解决：LangFuse 只把当前行为观测得更清楚，MCP 只把当前能力暴露给更多客户端，二者都不修正确性。直接做 P2 会得到"可观测、可调用、但回答仍不可靠"的系统。

同时，RT 清单里混着两类性质不同的工作：一类是**修现有能力的契约正确性**（不撒谎、诚实 partial、mode 一致、policy-refusal、fail-fast），低风险、无需新架构；另一类是**长新能力**（多语言摄取、仓库级 inventory、以及让 Agent 真正动态调用工具），高风险、触碰 D6 与依赖门禁。把两类焊进一个阶段，会得到一个既做不完、又无法快速投递的巨型 Gate。

## 决策

### 1. P1 保持关闭，本 ADR 只新增阶段

继承 ADR-0009 §1：P0/P1 的目标、范围、契约、任务与 Gate 不变。本 ADR 不追溯否定或重开 P1；RT-01～RT-23 是 post-P1 使用发现，只驱动新阶段，不回改 P1 验收结论、不重跑 P1 holdout。

### 2. 新增 G1.5：P1.5 真实仓库可靠性/诚实加固（投递前硬 Gate）

在 P1 与 P2 之间插入 P1.5，只做**契约正确性**修复：RT-01/02/03/08/15/16/18/19/20/22/23。目标是宁可给出范围准确的 partial/refusal/policy-refusal，也不交付"full 但没满足指定证据"、把已索引内容说成不存在、与 mode 冲突的绝对结论、未经代码验证的安全保证，或把已有生产证据的子答案整体清空。

P1.5 **在 D6 之内**：仍恰好 4 个在线 LLM 调用点、单 run ≤6 供应商请求、控制流由确定性代码判定。允许扩展 plan/evaluate/generate 的结构化输出 schema 与 Prompt（证据类型约束、`not_found` 分类、覆盖矩阵）——这是更丰富的结构化输出，不是工具调用，不突破 D6。PROMPT_VERSION 递增是预期的。

### 3. 新增 P1.6：仓库级证据能力 + 有界工具调用（能力增量）

P1.5 关闭后进入 P1.6：RT-05/06/13/17/21 + 动态工具调用。把仓库级确定性证据（manifest/symbol/annotation inventory、精确文件/类/方法/注解查找、按 commit 与目录范围的覆盖计数）**做成一组只读工具**，由 LLM 在一个**有界子循环**内经 function-calling 自主选择调用；宏观控制流（是否继续、何时停、预算）保持确定性。这既修 RT-21 的全局否定/穷举缺口与 RT-06 的方法级证据缺口，也补上"真正动态工具调用"的能力。多语言摄取（`.vue/.ts/.tsx/.sql`，RT-13）为 P1.6 内的独立可裁量工作流。

P1.6 的有界工具调用**窄修订 D6**（把"子循环内下一步取哪个只读工具"下放给模型，其余保持确定性），由 P1.6 自己的 ADR 承载；本 ADR 只声明方向，不预先松绑 D6，不预先开放任何 shell/写工具。

### 4. 重排可投递线：交付提前到 P1.5 之后

修订 ADR-0009 §2 的可投递硬前置：

- **原**：P1 + P2-A LangFuse + P2-B MCP 全部验收后投递。
- **新**：P1 + **P1.5** 关闭后即达可投递线，进入 **G4-early**（README/架构图/评测报告/演示/简历口径）开始投递；P1.6、P2-A LangFuse、P2-B MCP、P2-C 作为投递后按 Gate 推进的强化项。

理由：P1.5 关闭后已是"边界诚实、可回放、有评测 Gate"的检索型 agent，配合 post-P1 对抗测试记录，本身即强投递证据；LangFuse/MCP 是锦上添花，不应作为开始投递的前置。P2-A/P2-B 仍保留为强 Gate 能力，只是不再阻塞投递启动。

### 5. 先冻结 Evaluation-v1.5，再动代码

动任何 src/Prompt 前完成：把 18 条 post-P1 复现路径转为正式回归集；补自然问法、合法安全咨询、真正无资料等反例；每题预登记必需证据、禁止替代证据、预期 mode 与关键符号；分开统计 retrieval / evidence-selection / claim-support / final-consistency。不重跑、不据此调优已使用的 P1 holdout；另建 v1.5 dev/holdout。

### 6. 依赖门禁

P1.5 不新增运行依赖（契约修复在现有栈内完成）。P1.6 的多语言摄取需新增 tree-sitter 语言 grammar，走 P1.6 ADR 逐项核查。P2-A/P2-B 的 LangFuse/MCP SDK 解禁仍走各自 ADR（不变）。

## 后果

### 正面

- 核心问答正确性在投递前被硬 Gate 兜住，避免"可观测可调用但不可靠"。
- 低风险契约修复与高风险架构变更解耦：P1.5 先建回归网，P1.6 在稳定契约上再改架构，回归可定位。
- 投递启动从"做完 LangFuse+MCP"提前到"P1.5 关闭"，缩短求职启动。
- P1.6 一步同时兑现 RT-21 修复、方法级证据修复与"真正动态工具调用"能力。

### 代价与风险

- 插入两个阶段延后了 P2-A/P2-B 的落地时间。
- P1.5 会使 PROMPT_VERSION 递增、P1 的 Prompt 冻结在新阶段失效（P1 验收结论不受影响）。
- P1.6 的工具调用引入不确定性，必须以 P1.5 冻结的 Evaluation-v1.5 作回归网，并在 P1.6 ADR 明确 D6 窄修订边界。
- 可投递线的重排是对 ADR-0009 §2 的实质修订，须经用户批准。
