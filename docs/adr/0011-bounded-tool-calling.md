## 背景

### D6 为什么当初把工具调用挡在门外

ADR-0006 的核心不是「少调几次模型」，而是**让控制流可被确定性断言**：LLM 只返回受严格 Pydantic 校验的结构化信号，是否补检/生成/重生成/拒答由代码判定；单 run 供应商请求硬上限 6，任何异常路径都不得形成无界循环。这条边界在 P0/P1/P1.5 三个阶段一直成立，也是本项目能用 FakeLLM 精确断言节点序列、请求数、终态的原因。

代价是：**模型无法在一次 run 内按需索取它当下缺的那一份证据**。retrieve 由确定性代码调用、只做 top-k 语义检索，模型想问「`KnowledgeBaseService` 这个类到底在不在仓库里」时，没有任何途径可以问。

### 两条实测证据说明这个代价已经变成缺陷

**一、P1.5 U3.2 人工复核（2026-08-09，实测）**：`not_found` 里出现了 `KnowledgeBaseService`、`ConversationService`（c07）、`AsyncConfig`（e06）**三个仓库中根本不存在的类名**——在语料源 `rag知识库项目 @9bb79cd` 全仓 `find -name '<X>.java'` 与 `grep -rl 'class <X>'` 均零命中。另有一条把「会话删除的生产实现」绑到 `domain/Conversation.java`（实际在 `web/ConversationController.java` 与 `rag/RagService.java`）。

根因已在代码层坐实：`NotFoundDetail.refs` 由 `iter_path_tokens(text)` + `path_matches_token`（`src/devkb/agent/not_found.py:379` / `:393`）从**模型自己写的缺口句子**里抽路径 token 再与索引比对，而 `path_matches_token` **只判文件身份、不判命题**（该模块 `:461` docstring 已如实声明这条边界）。连带效应更糟：`basis` 因此被标为 `corpus_index`，输出变成「该路径已在当前项目索引中（状态 active），本轮未被召回」——**一句关于错误文件的、听起来已经过核验的断言**。

**关键在于这不是「模型不够聪明」，而是系统里没有任何组件能回答「这个符号存不存在」。** 评测层对同一批 104 条 `not_found` 判 `not_found_decidable_ok = 104/104` 全绿，因为可判定子集只覆盖「结构/枚举/静态后缀/已知路径措辞」；符号存在性属命题级，`not_found_proposition_undecided = 104` 全数路由人工兜底。

**二、RT-21（P1 后真实仓库测试，2026-07-23 归档）**：案例十一要证明 `src/main` 没有 Agent 实现、案例十二要闭合所有 Controller/endpoint，两者都需要带 commit、扫描范围、匹配规则与覆盖计数的**否定证明**。当时 planner 写出了 `grep`/`find` 这类遍历动作，但系统不会执行，于是既拿不到证明，也没有诚实的降级——RT-17 记录的正是同一形态：「计划必须区分『检索查询』和『真实可用的只读工具动作』」。

### 为什么必须窄修订 D6，而不是绕开它

有三条不动 D6 的路，都不成立：

1. **把 inventory 查询塞进确定性代码**（如 finalize 前统一校验所有符号）——能关掉「编造类名」，但关不掉 RT-21：穷举证明需要模型**按问题选择扫描范围与匹配规则**（哪个目录、哪个注解、哪种命名模式），这个选择无法预先枚举成固定流程。
2. **把 inventory 结果一次性塞进 Prompt**——仓库级 manifest/symbol 表远超上下文预算，且不知道该塞哪一部分；塞全量等于放弃检索。
3. **让 plan 一次性声明要查的符号**——plan 在 retrieve 之前执行，此时模型还没看到任何证据，不知道自己会缺什么。P1.5 的 `required_evidence` 解析已经证明了这条路径的上限：它只能解析用户**显式说出**的东西。

真正缺的是**「看到证据之后、生成之前，按需索取一份确定性事实」**这个能力。它在形态上就是有界的 function-calling 子循环。

## 决策

### 1. D6 窄修订的确切边界

**修订的只有一处**：在线 LLM 调用点由「恰好四类」扩为「四类 + 一个有界只读工具子循环」，并相应重设请求预算。

**下放给模型的，只有一件事**：在子循环内，**下一步调用哪个只读工具、传什么参数**。

**不下放、保持确定性的（逐条枚举，任何一条被突破即违反本 ADR）**：

- **是否进入子循环**——由确定性代码依据证据状态与预算判定，模型不能要求进入。
- **子循环何时结束**——由确定性代码判定，三个终止条件任一成立即结束：① 达到子循环轮次硬上限；② 模型本轮未请求任何工具；③ 全局预算不足以再发一次请求。**模型不能声明「我还要继续」来延长循环。**
- **宏观路由**——是否补检、生成、重生成、拒答、进入哪个终态，仍全部由确定性代码依据结构化信号与预算判定。模型不得返回下一节点名。
- **工具面**——只读白名单枚举，模型只能从枚举中选，不能构造新工具、不能传递可执行文本。
- **`project_id`**——由确定性代码注入，**不出现在任何工具的参数 schema 里**，模型无法指定或覆盖（D7 不变）。
- **预算计数器与 `run_id`**——模型不得覆盖（D6 原文保留）。

### 2. 预算：两层硬上限，都不可突破

| 项 | P0/P1/P1.5 | **P1.6（本 ADR）** |
|---|---:|---:|
| 单 run 发往供应商的总请求硬上限 | 6 | **11** |
| 其中：四个既有调用点的逻辑上限 | 6 | 6（**不变**） |
| 其中：工具子循环的请求上限 | — | **5** |
| 工具子循环内的工具执行轮次硬上限 | — | **4** |
| 检索轮次硬上限 | 2 | 2（**不变**） |

**11 的推导（不是拍脑袋）**：现有四调用点逻辑上限合计 `plan 1 + evaluate 2 + refine 1 + generate 2 = 6`，本 ADR 不动它。工具子循环最坏情形为「连续 4 轮都请求工具 + 第 5 次请求时不再请求工具而返回结论」= **5 次请求**。`6 + 5 = 11`。

**为什么子循环要单独设顶**：只提高总上限而不给子循环设独立上限，一个失控的子循环可以吃掉本该留给 generate 的预算，把「工具调用失败」放大成「回答生成不了」。

**`generate` 预留规则（这才是保证，「不侵蚀」只是它的推论）**：

> 在子循环的**每一轮开始前**，确定性代码检查
> `剩余全局预算 − 1（本轮将发出的请求）≥ GENERATE_RESERVE`；
> 不成立则**立即结束子循环**，携已获得的工具结果进入后续流程。
> `GENERATE_RESERVE` 为冻结常量，取 **1**（首次 generate）；若本 run 已发生过 L0/L1 违规、重生成仍可能被触发，则取 **2**。

早期草案写的是「两层上限使子循环最坏情形**不侵蚀**既有四调用点的预算下界」。该措辞被 2026-08-10 前置审查判为**把结论当机制**：`11 = 6 + 5` 的算术只在「每次请求恰好记一次、失败与重问的计数口径已定死」的前提下成立，而那套计数口径当时尚未冻结（见《P1.6实现规格》§6.5）。**非侵蚀不是设计前提，而是「预留规则 + 两层硬顶 + 冻结的计数口径」三者共同的推论**——三者缺一即不成立。本 ADR 因此把保证下沉到可执行的预留规则上，并要求实现规格冻结计数口径。

**计数口径（冻结，细则见《P1.6实现规格》§6.5）**：单点解析/传输失败最多重问 1 次，**重问计入全局预算与子循环请求上限，但不重置工具执行轮次计数**；工具执行失败本身不额外消耗请求（工具在本地执行）；**一次模型响应最多携带一个工具调用**，多于一个即判为协议违规、按解析失败处理。预算不足即走冻结默认值，不得无限重试。

### 3. 工具面：只读、白名单、参数严格校验

P1.6 只开放**仓库级确定性事实查询**类工具，全部只读、全部走 Repository 层（D7）：符号/注解/文件存在性与定位、按范围的覆盖计数与穷举。**具体工具清单、参数 schema 与返回契约由《P1.6实现规格》冻结**，本 ADR 只定边界。

**绝对禁止（不因任何实现便利放开）**：

- 任何 shell / 进程执行工具（含 `grep`/`find`/`cat` 的"安全包装"）——RT-17 记录的 planner 写出 `grep/find` 正是要**拒绝执行**并转为结构化工具，不是要实现它；
- 任何写工具（写文件、改数据库、发网络请求）；
- 任何跨 project 查询能力；
- 任何返回文档正文全文的工具（返回定位与计数，正文仍只经 retrieve 与引用校验路径）；
- 开放式无界 ReAct。

**工具执行失败**：确定性降级——记 warning、该轮工具结果标记为不可用、子循环继续或结束（按上限判定），**不重试、不无界**。工具永不执行被查询内容（解析器纪律不变）。

### 4. 与 D8 注入风险的关系

工具面仍是只读，D8 的「只读工具面消除执行类风险」结论不变。**新增一条必须在 P1.6 规格中承载的风险**：工具返回值会进入模型上下文，被检索文档中的指令载荷有了一条新的间接影响路径（模型可能因文档内容而选择某个工具/参数）。缓解：工具参数经严格 schema 校验且不含自由文本可执行字段；工具只返回结构化事实（路径、行号、计数、布尔），不回传文档正文；子循环有硬上限，最坏情形是浪费预算而非越权。**这条如实写入 README 与规格，不宣称已消除。**

## 依赖门禁

**本 ADR 覆盖的范围（ADR-0010 全范围经 2026-08-10 用户裁决收窄后）零新增运行依赖**，已逐条核实：

- **function-calling**：`openai>=2` 已在 `pyproject.toml` 运行依赖内（`src/devkb/llm.py:69` 使用 `AsyncOpenAI`），原生支持 `tools` 参数，无需新增 SDK。
  - ⚠️ **但项目自己的接缝还没开这个口，且供应商支持未实测**——2026-08-10 前置审查指出，本条原文只说了 SDK 一半的事：
    1. **`LLMClient` Protocol 只能返回文本**。`src/devkb/llm.py` 的 `complete(*, system, user, json_mode) -> LLMResult`，而 `LLMResult` 仅含 `text/model/usage`，**没有任何 `tool_calls` 表达**。P1.6 必须扩展这个 Protocol 与 `OpenAICompatLLM`——这是 D5「Protocol 只允许出现在 `embedding.py` 和 `llm.py` 两个接缝」允许范围内的**接缝内扩展**，不新增接缝，但**是一项必须在实现规格里冻结签名的设计工作**，不是"直接就能用"。
    2. **「SDK 支持 tools」≠「`deepseek-v4-flash` 已实测支持」**。ADR-0004 冻结的模型在本项目从未跑过 function-calling；且 P1.5 已实测该模型存在**间歇性把内容写进 `reasoning_content` 而让 `content` 为空**的行为（T31.2R-a）。**批准本 ADR 后、动 inventory 之前，须先做一次不含任何仓库数据的最小 function-calling 探针**（固定的假工具、固定问题，只验证：能否返回结构化 `tool_calls`、能否在收到工具结果后继续、失败形态是什么），结果写入《P1.6任务清单》T35 之前的 spike 记录。**探针失败即本 ADR 的可行性前提不成立**，须回到裁决而非硬做。
- **符号/注解抽取**：`tree-sitter>=0.25.2,<0.26` 与 `tree-sitter-java>=0.23.5` 已在依赖内，且现有 Java 解析器已识别 `class_declaration` / `method_declaration` / `annotation_type_declaration`（`src/devkb/ingest/java.py`），inventory 复用同一解析器。**tree-sitter 的 `<0.26` 上限继续有效**（0.26.0 在真实语料上 SIGSEGV，见 `benchmarks/p1_dependency_spike.md`），P1.6 不得借 inventory 之名放开该上限。
- **存储**：inventory 落 PostgreSQL 现有库（D1 单库多职责不变），走 Alembic 迁移，无新组件。

**被收窄出去的 RT-13 多语言摄取需要新增 tree-sitter grammar**，因此它不在本 ADR 范围内——这也是收窄的收益之一。若将来纳入，须另立 ADR 逐项核查依赖。

`langgraph`/`langchain-core` 的既有约束不变（D11③：不得替换 `LLMClient`/`Embedder`/Repository）。

## 后果

- **可确定性断言的部分不缩水**：宏观节点序列、请求总数、子循环轮次、终态仍可用 FakeLLM 精确断言。新增的不确定性被限制在「子循环内每轮选了哪个工具」这一点上，且该点有轮次上限、白名单和严格 schema 三重约束。
- **`confirmed_undocumented` 首次可产出**：P1.5 对该分类有「永不产出」的单测锁定（`src/devkb/agent/not_found.py` 枚举注释与配套用例）。P1.6 解锁它，但**只在有 inventory 支撑时**——每条必须绑定 commit、扫描范围、匹配规则与覆盖计数。**这是一次有意的契约变更，须在《P1.6实现规格》显式声明并改写那条 P1.5 冻结用例**，不得静默放开。
- **成本上界上升**：单 run 最坏请求数 6 → 11，接近翻倍。这是换取仓库级证据能力的明码代价，写入 README 能力/成本口径。
- **P1.5 的评测网继续有效**：Evaluation-v1.5 的 13 条契约题与反例在 P1.6 继续作回归网（ADR-0010 §风险已要求）；P1.6 另建 Evaluation-v1.6 覆盖新能力。
- **P1.5 冻结状态不受影响**：P1.5 仍是「Gate 未通过、5 达成 / 5 未达成」，本 ADR 不回改、不补勾。其未达成的第 1/2 条恰是 P1.6 的题目本身（命题级判定、仓库级 inventory）。

## 风险与缓解

| 风险 | 缓解 |
|---|---|
| 子循环把预算吃光，generate 无请求可用 | 两层硬上限 + 预算守卫的确定性裁剪顺序（优先保 generate，见 §2） |
| 模型滥用工具刷轮次而不收敛 | 轮次硬上限 4；达上限即结束并携已有结果继续，**不因未收敛而拒答** |
| inventory 与真实仓库不同步，产出「确定性」的错误否定 | 每条否定结论必须绑定 **commit + 扫描范围 + 匹配规则 + 覆盖计数**；inventory 与 documents 表同源同 commit，不一致即 fail-closed 不产出 `confirmed_undocumented` |
| 动态注册/反射等静态不可见的边界被当成「不存在」 | 沿用 RT-21 原判据：静态不可见边界**单独披露**，不计入否定证明的论域 |
| 工具返回值成为注入的新间接路径 | 见 §4：结构化返回、无正文回传、参数严格 schema、子循环有界；如实写入 README 不宣称消除 |
| 新能力掩盖 P1.5 未修的缺陷 | Evaluation-v1.5 作回归网全程复跑；P1.6 Gate 不得以新指标替代 P1.5 既有指标 |
