# ADR-0006：LLM 调用与确定性控制流边界

- 状态：已接受（2026-07-12 冻结；本文件为 T11.3 转写，内容以《范围冻结与架构决策》D5/D6 为准）
- 依据：《范围冻结与架构决策》D5/D6、《P1 Agentic RAG MVP 实现规格》§9/§10、ADR-0004

## 背景

P1 需要 LLM 做意图/子查询、证据评估、补检查询和回答生成，但不能把控制流交给未受约束的文本输出。若各节点和 SDK 独立重试，请求数还会在异常路径上相乘，使 token、成本、延迟与循环次数失控。

## 决策

### 在线 LLM 调用点恰好四类

| 调用点 | 逻辑调用上限 | 结构化输出失败后的冻结默认 |
|---|---:|---|
| `plan` | 1 | 原问题作为唯一 query，意图=`knowledge_qa` |
| `evaluate` | 每轮 1 次，最多 2 次 | 保守判为 `insufficient` |
| `refine` | 最多 1 次 | 保留原 query，不再补检 |
| `generate` | 初次 + 重生成，最多 2 次 | 第二次失败转确定性 partial/refusal |

冲突判定、NLI 和评测 judge 不在 P1 在线路径。

### 全局预算是供应商请求数，不只是节点数

- 单 run 发往 LLM 供应商的总请求硬上限为 **6**，包含格式失败重问和传输重试。
- 每个逻辑调用点最多重问 1 次，且只有全局预算仍有余量时才允许；重问同样记录 request、token、cost 和 latency。
- 若重试占用了原本可用于 refine 或 regenerate 的预算，预算守卫必须裁掉后续可选调用，转入冻结的 partial/refusal 默认路径。
- SDK 隐式重试不得绕过全局计数；任何异常路径都不得形成无界循环。

### 路由由确定性代码做决定

LLM 只返回受严格 Pydantic schema 校验的结构化信号。是否补检、生成、重生成或拒答，由代码根据检索轮次、全局预算、证据数量、结构化枚举和 L0/L1 结果判定。

LLM 不得返回下一节点名并被直接执行，不得覆盖 `project_id/run_id` 或预算计数器。LangGraph `recursion_limit` 仅是最后保险，不能代替业务上限。P1 不启用 checkpointer；单 run 原子执行，失败落 `failed` 终态。

## 后果

- 控制流可用 FakeLLM 精确断言节点序列、供应商请求数、重试数、终态和持久化记录。
- 全局 6 次上限意味着不能在同一 run 中对每个逻辑调用都用完重问机会；可预期的代价是局部故障时更早降级，收益是成本、延迟与循环均有硬上界。
- `evaluate` 的低信心只影响三态路由，不能额外触发重生成；只有 ADR-0008 的 L0/L1 违规能触发最多一次重生成。
- 格式错误、超时、检索故障和预算耗尽均必须有可回放的终态，不能留下永久 `running` 的正常失败用例。
