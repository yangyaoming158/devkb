# devkb 规划加强修复计划

> 状态：**已批准**；路线裁决阶段已于 2026-07-14 完成，后续仍受阶段 Gate 约束  
> 编写日期：2026-07-14  
> 适用范围：只调整 P2/P3 方向与后续规划治理；**P0/P1 的冻结范围、规格、任务和验收标准全部不变**。

## 1. 背景与修复目标

当前规划能在 P0/P1 覆盖 Python、PGVector、固定 RAG、Hybrid Search、LangGraph Agentic 工作流、引用与拒答、评测、测试、CI、Docker 等核心能力，但下列岗位能力尚未形成可执行、可验收的交付：

- LangFuse tracing、Prompt 版本与 evaluation 闭环；
- 可被真实客户端调用且具备只读安全边界的 MCP Server；
- Dify/n8n 中至少一种工具的实际集成；
- 单一云平台上的演示部署与基本监控；
- 真正的 Multi-Agent，而非单图多节点工作流；
- GraphRAG/Neo4j 的适用性实验与对照评测；
- LangChain/LlamaIndex 的有界、可解释使用；
- 教育行业场景演示。

本计划的目标不是把所有招聘关键词堆进主链路，而是重新安排 P2/P3 的优先级，尽快形成一条可投递、可演示、可诚实陈述的能力闭环。

## 2. 不可突破的边界

1. **P0/P1 不改**：不修改 `docs/P0实现规格.md`、`docs/P0任务清单.md`、`docs/Evaluation-v0.md`，也不改变《范围冻结与架构决策》中已经冻结的 P1 交付。
2. **当前执行不转向**：P0 期间仍只执行 P0 当前未完成任务；本计划不能成为提前添加依赖或代码的依据。
3. **主链路接缝不换**：保留 `llm.py` 的 `LLMClient` 和 `embedding.py` 的 `Embedder` 两个薄接缝，不用 LangChain/LlamaIndex 重写模型、Embedding、Repository 或检索主链路。
4. **确定性控制流不变**：LangGraph 负责状态与编排；循环、预算、降级、拒答和安全边界继续由确定性代码判定。
5. **单 Postgres 仍是主存储**：Neo4j 若进入 P3，只能作为实验性 sidecar，不替代 PostgreSQL/PGVector，不复制无关业务数据。
6. **不为关键词补技术**：不增加 Milvus、ChromaDB、Elasticsearch；Dify/n8n 只选一种；GraphRAG 和 Multi-Agent 均须有问题证据和评测收益。
7. **教育演示不冒充行业经验**：只能表述为“教育场景适配/演示”，不得写成教育行业商业项目或一年从业经验。

## 3. 可投递线

### 3.1 达线条件

达到以下条件后开始投递，不等待完整 P2/P3：

1. P1 全部验收通过；
2. P2-A LangFuse 最小闭环验收通过；
3. P2-B MCP 只读 Server 最小闭环验收通过；
4. README、架构图、评测报告和 5–8 分钟演示材料能完整复现上述能力；
5. 简历只陈述已通过验收的能力，未完成的云部署、Multi-Agent、GraphRAG 继续边投递边完成。

### 3.2 达线后的能力口径

- 可以写：Python Agentic RAG、PGVector、Hybrid/RRF、LangGraph、FastAPI、MCP、LangFuse、提示词设计与上下文管理实践、Evaluation、Docker/CI。
- 不可以写：Multi-Agent、GraphRAG/Neo4j、AWS/GCP/Azure 运维、LlamaIndex 复杂应用，除非对应后续 Gate 已通过。
- `Context Engineering（含对照实验）` 只有在 P2-C 第 4 项完成上下文策略与多模型对照报告后才能写入简历。
- 对 JD 的覆盖率只作为内部排序参考：宽口径约 8–9/12，严格按可独立证明的项目能力约 7–8/12；学历与“一年以上经验”不能由项目补齐。

## 4. 分阶段加强路线

### 4.1 P2-A：LangFuse 最小闭环（投递 Gate）

目标：把已有自建 run/step 轨迹与专业 LLM 可观测平台连接起来，形成“观察—评测—改进”的证据，而不是只展示一张 trace 截图。

最小范围：

- 一个请求对应一个 trace，LangGraph 节点、检索和 LLM 调用对应 span/generation；
- 记录模型名、Prompt 版本、tokens、cost、latency、错误类型和 run_id；
- 关联 Evaluation 数据集，至少完成一次基线与一次 Prompt/检索变更后的对照 run；
- 把引用有效率、拒答正确率或 groundedness 等已有评测结果写成 score；
- 默认不上传文档全文、API key、secret 或不必要的源码正文；
- LangFuse Cloud、开发实例或独立 compose profile 三选一，具体部署方式由阶段 ADR/规格裁决，不预先锁死。

验收证据：

- 一个成功 run 和一个故障/降级 run 可按 run_id 在本地轨迹与 LangFuse 间互查；
- 数据集对照报告可复现；
- 关闭 LangFuse 或网络失败时，主问答链路按既定策略降级，不因观测系统不可用而失败；
- 单元/集成测试不访问真实 LangFuse 服务。

### 4.2 P2-B：MCP 只读 Server（投递 Gate）

目标：把 devkb 已有只读查询能力通过标准协议开放，证明工具协议、安全边界与系统集成能力。

最小范围：

- 暴露 3 个有真实用途的只读工具，例如 `search_project_knowledge`、`read_chunk`、`get_run_trace`；
- 至少提供 1 个 resource，用于公开项目/证据结构说明；是否提供 prompt 由实际使用价值决定；
- 复用现有 Repository/project_id 隔离，不允许 MCP handler 绕过 Repository 直接构造 SQL；
- 对输入 Schema、最大 top_k、正文返回长度、超时、错误码和日志脱敏设确定性限制；
- 不提供写文件、执行命令、修改数据库、Git 写操作或任意 URL 抓取工具；
- 先以本地 stdio 或本地 Streamable HTTP 完成演示，远程鉴权不作为可投递 Gate。

验收证据：

- MCP Inspector 或一个真实客户端能发现并调用工具；
- 双项目隔离、越权 chunk_id、超长输入、超时和服务不可用均有测试；
- 工具调用能关联到 agent run/tool invocation/LangFuse trace；
- README 明确协议传输、安全边界和剩余风险。

### 4.3 P2-C：投递后高收益增强

P2-C 按下列顺序逐项裁决，不要求同时完成：

1. **教育场景演示语料**；
2. **单实例云演示部署**；
3. **n8n 集成**；
4. **Context Engineering 对照报告与多模型基准**；
5. **LlamaIndex 受控对照实验**；
6. 现有 P2 中经评测证明必要的 reranker、增量索引、冲突检测等能力。

#### 教育场景演示语料边界

- 不改变“软件项目知识助手”的主定位，也不替换 mini-mall 的主评测基线；
- 以独立 `project_id` 摄取一套小型、自编或许可清晰的课程知识库；
- 不使用真实学生个人信息、受版权限制的整本教材或伪造客户数据；
- 建议规模为 10–20 份 Markdown、10 道可回答题和 3 道不可回答题；
- 复用现有摄取、隔离、引用、拒答和评测链路，不为教育场景增加专用业务代码；
- 演示结论只证明系统可适配教育语料，并额外验证多项目隔离。

#### 云部署硬边界

云部署只做“一个云平台、一个区域、单实例演示部署 + 基本监控”：

- Docker/Compose 或等价单实例容器部署；
- `/healthz`、结构化日志、CPU/内存/磁盘/服务可用性基本指标；
- 环境变量/Secret 注入、HTTPS 或受控访问、最小网络暴露；
- 一次从干净环境部署或重新发布的可复现记录。

明确不做：Kubernetes、集群、高可用、多区域、自动扩缩容、正式备份体系、恢复演练、完整灾备、生产 SLA。云厂商快照或手工导出可以作为非 Gate 备注，但不得扩大为运维子项目。

#### n8n 硬边界

- 只实现一个有业务意义的集成工作流，例如“文档变更 webhook → 调用 ingest → 查询结果 → 触发评测 → 失败通知”；
- n8n 不复制 RAG、Agent 或评测核心逻辑，只负责编排外部事件和系统 API；
- 不同时引入 Dify；若后续岗位明确要求 Dify，另做独立小实验，不进入主项目。

#### LangChain/LlamaIndex 硬边界

- P1 使用 LangGraph 时允许自然使用 `langchain-core` 的消息、工具或 Runnable 基础类型；
- 禁止以 LangChain ChatModel、VectorStore、Retriever 重写 `LLMClient`、`Embedder`、Repository 和现有检索接口；
- LlamaIndex 只允许在隔离的 benchmark/experiment 中对同一语料完成一种摄取或检索对照；
- LlamaIndex 实验必须报告质量、延迟、可控性与迁移成本，不能只以“成功跑通”作为完成判据。

### 4.4 P3：Multi-Agent + GraphRAG（非投递前置）

进入 P3 前必须先收集一组 Hybrid RAG 明显不足的问题，例如跨文档依赖、接口—服务—数据库关系、变更影响范围或调用链问题。

GraphRAG Gate：

- 先定义实体、关系和支持的问题类型，再决定是否引入 Neo4j；
- 使用同一问题集比较 Hybrid RAG 与 GraphRAG，至少报告 Recall/答案正确性、引用支持度、延迟、成本和索引开销；
- 若没有稳定收益，保留负结果报告并停止引入，不把 Neo4j 并入默认运行栈；
- 若有收益，Neo4j 仍只保存关系检索所需图数据，文档、chunk、run 和权限真相源继续在 PostgreSQL。

Multi-Agent Gate：

- 至少有两个职责、工具集或上下文明显不同的专业 Agent，不能把普通 LangGraph 节点改名为 Agent；
- 推荐候选为 Vector Retrieval Agent、Graph Retrieval Agent、Evidence Critic，由 supervisor 选择或汇总；
- 需要证明相对单 Agent 工作流在目标问题上有收益，且额外 token、延迟和失败面可接受；
- 继续执行只读工具面、有界调用次数、确定性预算、失败降级和人工确认边界。
