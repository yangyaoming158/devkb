## 1. 目标与范围

P1.6 只做**一件事**：给系统一种它现在完全没有的能力——**回答关于仓库整体的确定性事实**（这个符号存不存在、这类东西一共有几个、这个范围里有没有）。P1.5 修的是「说出口的话要诚实」，P1.6 补的是「有些话现在根本没有依据可说」。

P1.6 冻结交付（全部在 ADR-0011 修订后的 D6 与**零新增运行依赖**之内）：

1. **仓库级 inventory**（manifest / symbol / annotation）随摄取确定性构建，与 documents 同源同 commit（RT-21）；
2. **符号存在性校验**接管 `not_found` 的 refs 绑定，关闭 U3.2 实测的编造类名与绑错目标（`U32-P16-01/02`）；
3. **有界只读工具子循环**：模型在证据不足时按需索取仓库级事实，轮次与预算双硬顶（ADR-0011）；
4. **refine 的符号约束**：改写查询中的路径/符号只能来自用户问题、已检证据或 inventory（RT-17）；
5. **全局否定/穷举的确定性证明**：`confirmed_undocumented` 首次可产出，每条绑定 commit + 扫描范围 + 匹配规则 + 覆盖计数（RT-21）。

**明确不做**（见 §10）：多语言摄取（`.vue/.ts/.tsx/.sql`，RT-13）、检索机制改进（RT-06 及 RT-05 检索层 metadata 权重）、`claims` 未进正文（`U32-P16-03`）、在线 L2/NLI、LangFuse、MCP、UI/SSE、云部署。**上述三项经 2026-08-10 用户裁决移出 P1.6**（ADR-0011 §修订/被取代内容已登记该收窄）。

## 2. 继承与兼容性

## 4. 仓库级 inventory（RT-21）

### 4.1 三类事实

| 事实 | 内容 | 来源 |
|---|---|---|
| **manifest** | 已摄取文件清单：`rel_path`、`content_hash`、`suffix`、active 状态 | 摄取管线，与 `documents` 同一次写入 |
| **symbol** | 类 / 接口 / 枚举 / 注解类型 / 方法：名称、kind、所属包与文件、起止行 | 现有 tree-sitter Java 解析器（`src/devkb/ingest/java.py` 已识别 `class_declaration` / `method_declaration` / `annotation_type_declaration`） |
| **annotation** | 注解**使用**：注解名、被注解的目标符号、文件与行 | 同上 |

### 4.2 快照身份与状态（**本节是否定证明的唯一真相源**）

早期草案只写「与 documents 同源、同一 commit」，被 2026-08-10 前置审查判为**没有可实现的真相源**（`PG-P16-01`）。实测的三条仓库事实：

| # | 事实 | 证据 |
|---|---|---|
| A | 语料视图 manifest **已记录** `source_commit` 与 `source_worktree_dirty` | `tools/build_corpus_view.py` 的 manifest 构造块 |
| B | 摄取管线**从不读取** manifest；`Document` 模型**没有任何 commit 字段** | `src/devkb/ingest/pipeline.py`（全文无 manifest 引用）、`src/devkb/models.py` 的 `Document`（字段为 `id/project_id/rel_path/title/doc_type/content_hash/…`） |
| C | 摄取**逐文件**幂等，**不清理**新视图中已删除的旧 active 文件 | `src/devkb/ingest/pipeline.py` 只按 `existing.status == "active"` 做单文件比对，无全量对账 |

因此「同一 commit」在当前实现里**无处可查**。P1.6 必须先建立快照身份，否则一切否定证明都建立在一个不存在的前提上。

> **第二轮前审（`PG-P16-01`）判定本节仍未闭环**，并额外坐实四条：① 早期草案写「摄取从 manifest 读入前四项」，而前四项含 `snapshot_id`/`project_id`——**这两项根本不在 manifest 里**；② manifest **不持久化 include/exclude 规则**（顶层键只有 `version/source/source_commit/source_worktree_dirty/built_at/total/counts/files`），而 §4.3 的六项披露需要它；③ manifest 存**原始字节** sha256（`tools/build_corpus_view.py` 的 `source_digest`），摄取存**规范化文本** sha256（`pipeline.py` 的 `_normalize_text(...).encode("utf-8")`）——**两者构造上不同口径**，非 UTF-8 文件下必然不等（既有 GBK 摄取测试为证）；④ `Document` 唯一键为 `(project_id, rel_path)` 且原地 `upsert`——**新 building 快照会直接改写上一份 ready 引用的数据**，「上一 ready 继续服役」无从成立。以下为闭环后的冻结要求。

#### 4.2.1 manifest v2 合同（由 `tools/build_corpus_view.py` 产出，先于摄取）

在现有键之外**新增三项**，构成 manifest v2（旧 manifest 视为 v1，**只可用于不可证明摄取**，见 4.2.5）：

| 新增键 | 内容 | 用途 |
|---|---|---|
| `manifest_version` | 固定 `2` | 版本判别 |
| `include_rules` / `exclude_rules` | 从视图 TOML **逐字持久化**的 include patterns 与 exclude（hidden / dir_names / file_names） | §4.3 六项披露的唯一合法来源——**规则不落盘就无法在事后证明扫描范围** |
| 每条 file 的 `source_sha256` | 原始字节 sha256（即现有 `sha256` 键，**改名以消除口径歧义**） | 与摄取侧的原始字节 hash 对账 |

#### 4.2.2 双 hash 口径（消除 ③）

- **`source_sha256`**（原始字节）——摄取时**新增保存**一列，**只用于 manifest 对账**。
- **`content_hash`**（规范化文本）——`Document` 既有列，**语义与用途完全不变**，继续承担幂等与变更检测。P1.5 冻结行为零改动。
- **对账只比 `source_sha256`，绝不比 `content_hash`。** 两者是不同的东西，混用即产生假失败。

#### 4.2.3 版本化实体与原子发布（消除 ④）

1. **`documents` / `chunks` / inventory 三类实体全部携带 `snapshot_id`**；`documents` 唯一键由 `(project_id, rel_path)` 改为 **`(project_id, snapshot_id, rel_path)`**。
2. **写入即 staging**：`building` 快照的数据写在自己的 `snapshot_id` 下，**与上一份 `ready` 物理并存、互不覆盖**。
3. **发布是指针切换**：project 持有一个 `current_ready_snapshot_id` 指针；发布 = **单事务内**校验通过后把指针指向新快照。失败则指针不动、新快照置 `failed`，**旧 ready 数据完好无损**。
4. **删除对账因此退化为结构性质**：新快照的路径集合**就是** manifest 入选集合，天然不含已删除文件——不需要任何"清理旧 active"的过程性步骤。**这是版本化带来的红利：把一个容易漏做的过程，变成一个不做就不成立的结构。**
5. 旧快照数据的保留与清理是**运维项**，不影响正确性；清理不得删除仍被指针引用的快照。

#### 4.2.4 状态机与对账

- 三态 `building` / `ready` / `failed`，迁移只允许 `building → ready | failed`；**`ready` 不可原地修改**。
- **发布前的联合对账（三项全过才可 `ready`）**：① `documents` 的 active 路径集合 == manifest 入选路径集合；② 每条 `source_sha256` 与 manifest 一致；③ inventory 的 `snapshot_id` 覆盖面与 `documents` 一致。任一不过即 `failed` 并记录差集，**不静默接受**。
- **中断恢复**：残留的 `building` 快照在下次摄取或服务启动时置 `failed`；**不得永久停留在 `building`**。
- **单 run pinning**：问答在 run 开始时解析一次 `current_ready_snapshot_id` 并在本 run 内固定；中途新快照发布不影响本 run。

#### 4.2.5 可证明性标志（替代早期草案的"拒绝摄取"，消除自相矛盾）

早期草案同时写了「manifest 缺失即**拒绝摄取**」与「manifest 缺失时**仍可正向查询**」——两者不可能同时成立（拒绝了就没有数据可查），且**会静默破坏既有的裸目录摄取合同与相关冻结测试**（`tests/integration/test_ingest.py` 依赖直接 ingest 目录）。

**冻结口径**：

> **裸目录摄取继续支持，行为逐字不变**；但其产生的快照 `provable = false`。
> `provable = true` 当且仅当：manifest v2 存在 ∧ `manifest_sha256` 校验通过 ∧ 联合对账全过 ∧ `source_worktree_dirty = false`。

- **`provable = false` 的快照只允许正向查询**（"X 在 Y 处"），**禁止一切否定与穷举证明**，proof `verdict` 上限为 `unavailable`，并在回答中声明降级原因。
- **这不是契约变更**：既有摄取路径的行为、返回值与冻结测试全部不变，新增的只是一个标志位与它带来的**能力上限**。

#### 4.2.6 其余

- 解析失败的文件计入该快照的**未覆盖清单**并可查询——「解析失败」与「不存在」必须可分，且**不进入否定证明的论域**（§4.3）。
- 落 PostgreSQL 现有库（D1 单库多职责不变），走 Alembic 迁移，`project_id NOT NULL + FK`（D7）。

### 4.3 覆盖边界（本节是本阶段最容易出错的地方）

早期草案写「inventory 的论域 = 已摄取后缀的文件」，被 2026-08-10 前置审查判为**把后缀当成了完整论域**（`PG-P16-02`）。实测反例：`corpora/mini-mall-p1.toml` 的视图定义里，Markdown 的 include 只有 `docs/**/*.md` 与**仅根级** `README*.md`，另有 exclude 强制排除隐藏路径、`node_modules/target/build/dist`、以及 `CLAUDE.md`/`AGENTS.md`/`TASKMASTER.md`。**因此一个 `.md`、`.yml` 或 `.java` 即使后缀受支持，也完全可能根本不在视图中**——按旧论域，系统会对一个从未被索引的文件理直气壮地说"不存在"。

**冻结论域定义**：

> inventory 的论域 = **某个 `ready` 快照的 manifest 入选、且成功解析、且当前 active 的文件**。
>
> 「后缀受支持」既非充分也非必要条件——它只是 manifest 入选的**其中一道**筛子。

因此：

- **任何否定或穷举结论必须同时披露六项**：`snapshot_id` + `source_commit`、`view_version`、**include / exclude 规则**、生效后缀集合、解析失败与截断情况、覆盖计数。少任一项即不得产出，退回条件式措辞。**这是硬性内容，不是修辞。**
- **五类必须有反例的边界情形**（每类至少一条单测 + 至少一条 v1.6 评测题）：
  1. **后缀受支持但被 include 漏掉**（如非 `docs/` 下、非根级的 `.md`）；
  2. **后缀受支持但被 exclude 排除**（隐藏目录、`target/`、`CLAUDE.md`）；
  3. **未摄取格式**（`.vue/.ts/.tsx/.sql`）；
  4. **manifest 入选但解析失败**（进未覆盖清单，不进论域）；
  5. **上一快照 active、本次已删除**（删除对账后不得再被当作存在）。
  前两类的正确回答与第 3 类**同型但理由不同**，措辞须区分：第 1/2 类是「该文件不在本项目的语料视图范围内（view `X`，include/exclude 见披露）」，第 3 类是「该格式不在摄取范围」。**两者都不得说成"仓库里没有"。**
- 对 `.vue/.ts/.tsx/.sql` 等未摄取格式，inventory **没有任何发言权**。问「有没有 Vue 组件」时，正确回答是「该格式不在摄取范围、未纳入索引，本系统无法确认仓库是否包含此类文件」（沿用 P1.5 的 `unsupported_or_not_ingested` 条件式措辞 + 覆盖披露），**绝不能回答"不存在"**。
- 动态注册、反射、注解处理器生成等**静态不可见**的边界，单独披露、不计入否定证明的论域（RT-21 原判据）。

> **为什么单列这一节**：inventory 让系统第一次有能力说"没有"。而"没有"是本项目最危险的一句话——P1 后真实测试的 RT-02/RT-15 就是「把已索引内容说成不存在」，P1.5 花了一整个阶段把它压住。**新能力必须带着旧纪律上线**，否则 P1.6 会以更权威的口气重犯 P1 的错。

### 4.4 证明载体：版本化结构化 proof（**先有结构，才有文案**）

早期草案要求「每条否定绑定 commit + 范围 + 规则 + 覆盖计数」，却只说 API「增字段」，没冻结承载它的结构——被 2026-08-10 前置审查判为**判据无处落地**（`PG-P16-03`）。实测：现有 `NotFoundDetail`（`src/devkb/agent/not_found.py`）字段仅 `text` / `category` / `source` / `basis` / `refs` / `original_text` 六项，**无一能表达 snapshot、扫描范围、匹配规则或计数**。

**冻结要求**：新增一个**版本化**的结构化 proof 类型（严格 Pydantic、`extra="forbid"`），作为 Answer JSON 的**平行新增字段**（对既有消费者纯加法，P1.5 契约只增不删）。最小字段集：

| 组 | 字段 | 说明 |
|---|---|---|
| **标识** | **`proof_id`** | **稳定唯一标识（run 内唯一），供 `NotFoundDetail.proof_id` 引用——没有它，G2/G3 说的「其 proof」在同名主体或重复缺口时选不中唯一一条** |
| 版本 | `proof_schema_version` | 独立版本号，与 `ANSWER_SCHEMA_VERSION` 解耦；键集合变化即升版。**初始值冻结为 `p1.6-proof-v1`** |
| 快照 | `snapshot_id`、`source_commit`、`source_worktree_dirty`、`view_version`、`manifest_sha256`、**`provable`** | 全部来自 §4.2 的快照；`provable = false` 时 `verdict` 上限为 `unavailable` |
| 主体 | `subject_kind`（**封闭枚举，恰四值**：`symbol` / `annotation` / `path` / `count`）、`subject`、`subject_origin`（**封闭枚举，恰三值**：`user_question` / `retrieved_evidence` / `inventory`） | 早期草案的 `symbol/annotation/path/…` **带省略号，不是封闭枚举**（`PG-P16-03`），已收敛为四值。`subject_origin` 是 §5 的判别力所在——**模型自造的符号不属于任何一类，见 §5.3 情形 4** |
| 结论 | `verdict`（枚举：**`found` / `not_found` / `out_of_scope` / `unavailable`**） | 四态，**不是布尔**。`out_of_scope`＝不在论域（§4.3 五类边界）；`unavailable`＝降级状态下判不了（§4.2 第 5 条） |
| 范围 | `scan_scope`（目录前缀等）、`effective_suffixes`、`include_rules`、`exclude_rules` | §4.3 六项披露的机器可读来源 |
| 规则 | `match_rule`（枚举，非自由文本）、`match_params` | 匹配规则必须可枚举，禁止自由文本规则 |
| 计数 | `scanned_count`、`matched_count`、`parse_failed_count`、`excluded_count` | 分母/分子分离，供评测直接取数 |
| 完整性 | `complete`（bool）、`truncated`（bool）、`truncation_reason` | 截断必须可见；`truncated=true` 时 `complete` 恒 `false` |
| 位置 | `locations`：`rel_path` + `start_line` + `end_line` | **行号一律 1 基**，与既有引用契约同口径 |

**Answer 字段名与关联（冻结）**：

- Answer JSON 新增平行字段 **`proofs`**：`list[Proof]`，纯加法，既有字段一律不动。
- `NotFoundDetail` 新增**可选**字段 **`proof_id: str | None = None`**（纯加法，P1.5 既有六字段与其语义不变）。
- **基数冻结**：
  - 一条 `NotFoundDetail` 对应 **0 或 1** 条 proof。`proof_id = None` 表示本条未经 inventory 判定（例如 §5.3 情形 4 被泛化后的条目、或 `provable=false` 下的条目）。
  - 一条 proof 可被 **0 或 1** 条 `NotFoundDetail` 引用；**不允许多条 detail 共用同一 `proof_id`**——同一主体被两条缺口分别提及时产出两条 proof，各自独立计数。
  - `proofs` 中允许存在**未被任何 detail 引用**的条目（例如工具子循环查到但最终未形成缺口的正向事实），它们**照常计入 Gate 分母**。
- **重复主体**：同一 `(subject_kind, subject)` 在一次 run 内出现多次时，**每次产出独立 proof**（各有独立 `proof_id` 与独立计数），**不去重、不合并**——合并会掩盖"同一个东西在不同缺口里结论不一致"这一信号。
- **泛化条目**（§5.3 情形 4）：`NotFoundDetail.proof_id = None`，且**不产出 proof**——对模型自造的名字不做任何判定，自然也没有判定记录。

**两条硬约束**：

1. **用户可见文案由该结构确定性渲染**，不由模型自由撰写——渲染函数是纯函数、有单测、且**渲染不出结构里没有的信息**。这与 P1.5 的 `coverage_disclosure()`/`verified_scope_note()` 同型（确定性文案 + 可证事实）。**该渲染一致性由 G5 承载出口**（见 §12.1），不是无人验收的散文要求。
2. **`verdict` 为 `not_found` 且 `complete=false` 时，禁止渲染为否定结论**——降级为「本次扫描不完整（原因）」。**不完整的扫描不构成否定证明**，这一点比任何措辞都重要。

## 5. 符号存在性校验与 `not_found` refs 修复（U32-P16-01/02）

### 5.1 要修的实测缺陷

U3.2 人工复核（2026-08-09，`evalsets/reports/p1.5-manual-check.md`）实测：

- `not_found` 出现 `KnowledgeBaseService`、`ConversationService`（c07）、`AsyncConfig`（e06）——**三者在语料源仓库全仓零命中，属编造**；
- c07 把「会话删除的生产实现」绑到 `domain/Conversation.java`，实际在 `web/ConversationController.java` 与 `rag/RagService.java`；
- 连带把 `basis` 标为 `corpus_index`，输出「该路径已在当前项目索引中（状态 active）」——**一句关于错误文件的、听起来已核验的断言**。

根因：`NotFoundDetail.refs` 由 `iter_path_tokens(text)` + `path_matches_token`（`src/devkb/agent/not_found.py:379` / `:393`）从模型自写的缺口句子抽路径 token 再匹配索引，而 `path_matches_token` **只判文件身份、不判命题**。

### 5.2 身份 ≠ 命题（**本阶段最容易越界的一步**）

早期草案承诺「c07 绑到真实删除实现而非 `domain/Conversation.java`」，被 2026-08-10 前置审查判为**没有对应机制**（`PG-P16-05`）。理由在现有代码里逐字写着：

> 「确定性代码无法证明"该缺口所述命题已被正文支撑"（`path_matches_token` 只判文件身份、L1 只判引文逐字子串）」
> —— `src/devkb/agent/not_found.py` `_render` 系列函数 docstring

inventory 能证明 **`Conversation` 这个符号位于某文件**；它**证不了那个文件"实现了会话删除"**。后者是命题级判断，需要 L2/语义能力——D9 明确不在在线路径。**把"符号定位"当成"命题实现位置"，正是 `U32-P16-02` 缺陷的同一形态，只是换了个更权威的来源。**

因此 `U32-P16-02` 的验收目标**收窄为可实现的形态**：

> **不是**「自动绑到真实的删除实现」，**而是**「**错误路径不得被绑定**；命题无法证明时 `refs` 为空并条件式降级」。

### 5.3 判定表（冻结）

缺口句子中点名的符号/路径，**先经 §4.2 的 `ready` 快照与 inventory 判定，再决定措辞与 refs**：

| # | 情形 | `subject_origin` | refs | `verdict` | 措辞 |
|---|---|---|---|---|---|
| 1 | 符号来自用户/证据/inventory，且 inventory 唯一定位 | 三者之一 | 绑定该符号的**真实定位** | `found` | 「符号 X 位于 …，本轮未召回，属当前证据缺口」——**只陈述符号位置，不声称该处实现了缺口所述命题** |
| 2 | 同上，但多处同名 | 三者之一 | 绑定**全部**命中（有上限，超限置 `truncated=true` 并声明） | `found` | 同上 + 声明命中多处，**不替用户选哪一处是"真正的实现"** |
| 3 | 符号来自用户/证据，inventory 查无 | `user_question` / `retrieved_evidence` | 空 | `not_found` | 可判定负结论，须携完整 proof（§4.4 六项披露） |
| 4 | **符号是模型自造**（不在用户问题、不在已检证据、不在 inventory） | 三者皆非 | 空 | — | **删除或泛化该符号名**，缺口降级为不点名的表述（如「相关生产实现未在本次证据中出现」）。**禁止渲染成"索引中不存在 X"**——见下方硬约束 |
| 5 | 不在论域（§4.3 五类边界之一） | 任意 | 空 | `out_of_scope` | 区分「不在语料视图范围」与「格式未摄取」两种理由，均不说"仓库里没有" |
| 6 | 处于 §4.2 第 5 条的降级状态 | 任意 | 空 | `unavailable` | 「本次无法判定（原因）」，**禁止任何否定与穷举结论** |

**三条硬约束**：

1. **只有 `subject_origin ∈ {user_question, retrieved_evidence, inventory}` 的具体符号才能进入最终 `not_found`。** 模型自造的符号名一律删除或泛化（情形 4）。
2. **对自造符号，"inventory 查无"不得被包装成权威负结论。** `KnowledgeBaseService` 从来不是用户问的、也不在证据里——对一个凭空冒出来的名字宣布"索引中不存在"，是**用权威口气回答一个没人问过的问题**，比 P1.5 的编造更难被发现。`U32-P16-01` 的正确修法是**让它根本不出现在 `not_found` 里**，不是给它配一份否定证明。
3. **`path_matches_token` 不再单独决定 refs**（可保留为候选生成，但必须经 inventory 确认）；**`basis` 如实反映校验来源**，经 inventory 确认者记新增来源（如 `symbol_inventory`），未经确认者**不得**标为 `corpus_index`。

**反过拟合反例（必须有单测）**：同名类分布在多个包下、内部类 / 嵌套类、泛型与数组类型、方法重载、大小写差异、`com.example` 之类的包名片段（P1.5 已有的词法防御不得回退），以及**情形 4 的自造符号必须被删除/泛化而非否定**。

## 6. 有界只读工具子循环（ADR-0011）

### 6.1 位置与触发

- **新节点，位于 evaluate 之后、generate 之前**。理由：模型必须**先看到证据**才知道自己缺什么；plan 阶段（retrieve 之前）无法预知缺口——P1.5 的 `required_evidence` 解析已证明那条路径只能解析用户显式说出的东西。

**进入谓词（冻结，四项合取）**：

```text
enter_tool_loop  ⟺  E1 ∧ E2 ∧ E4 ∧ E5

E1  evaluate 结构化输出为 insufficient/partial，或覆盖矩阵存在未覆盖 aspect
E2  本 run 尚未进入过子循环          （每 run 至多进入一次，非重入）
E4  存在**确定性可用工具集**——即当前快照状态下至少有一个工具未被禁用（见下）
E5  剩余全局预算 − 1 ≥ GENERATE_RESERVE
```

> **早期草案的 E3（「由确定性分类器判定缺口是否 inventory 可答」）已删除**（2026-08-10 第二轮前审 `PG-P16-04`，执行者第一轮即主动申报过同一风险）。删除理由有二：① 它没有冻结输入字段、算法或封闭 token 规则，只写了"符号/路径/注解/计数四类"——若读取 `missing_aspects` 则输入本身就是模型自由文本，**会重演 `evidence_types.py` 的规则堆叠**（该文件 1006 行、40+ 正则、6 轮审查改写 4 次，已被诊断为过度设计典型）；② 它带来的收益只是"少进一次子循环"，而**轮次上限本来就把最坏情形兜住了**。**用一个证不出边界的分类器去省 4 次请求，是拿正确性换成本。**

**E4 与降级的关系（消除早期草案「E4=ready 既是必要条件、又说不成立时仍可进入」的自相矛盾）**：

| 快照状态 | 可用工具集 | E4 | 本轮 proof `verdict` 上限 |
|---|---|---|---|
| `provable = true`（§4.2.5） | 四个工具全可用 | ✅ | 无上限 |
| `provable = false` 或无 `ready` 快照 | **只有** `lookup_symbol` / `check_path`（正向查询）；`list_annotated` / `count_matching` **禁用** | ✅（集合非空） | `unavailable` |
| 无任何快照（未摄取） | 空集 | ❌ **不进入** | — |

**E4 是「可用工具集非空」，不是「快照 ready」**——这样降级路径与进入谓词不再打架。

**结束条件（三条，全部不依赖模型选择；这是 `PG-P16-04` 的核心修正）**：

```text
T1  轮次达上限 4
T2  剩余全局预算 − 1 < GENERATE_RESERVE
T3  **确定性收敛**：本轮工具结果使「待判定主体集合」变空
    （由确定性代码检查每个主体是否已有 proof，不读模型任何自述）
```

> **模型返回 0 个 tool_call 不再是结束信号。** 早期草案把它写成「→ generate」，被审查者按执行者自己设的 S3 标准构造出反例：**相同状态下，模型返回 1 个 tool_call 则继续、返回 0 个则结束——这就是模型在决定控制流**，与 ADR-0011「只下放工具与参数」直接冲突。
>
> 现口径：**0 个 / >1 个 / 非法参数 / 非白名单工具名，一律归入「协议失败槽位」**——记 warning、本轮无工具结果、轮次 +1，然后**照常检查 T1/T2/T3**。模型可以浪费一轮，但**不能靠它结束循环**。代价是最坏情形多烧几次请求，上界仍是 4 轮；换来的是控制流不泄漏。

**状态转移表（冻结，行与行互斥且穷尽——早期草案的「合法调用 +1 轮」与「工具执行失败 +1 轮」会被同一次调用同时命中，已合并为完整结果行）**：

| # | 当前 | 完整事件（互斥） | 下一状态 | 非工具请求 | 子循环请求 | 轮次 |
|---|---|---|---|---:|---:|---:|
| 1 | `evaluate` 完成 | 进入谓词成立 | `tool_loop`（轮次=0） | — | — | — |
| 2 | `evaluate` 完成 | 进入谓词不成立 | `generate` | — | — | — |
| 3 | `tool_loop` | 恰 1 个 tool_call ∧ 参数合法 ∧ **工具执行成功** | 检查 T1/T2/T3 | +0 | +1 | +1 |
| 4 | `tool_loop` | 恰 1 个 tool_call ∧ 参数合法 ∧ **工具执行失败/超时** | 同上（结果标不可用） | +0 | +1 | +1 |
| 5 | `tool_loop` | 恰 1 个 tool_call ∧ **参数非法或工具名不在白名单** | 同上（**不调用 Repository**） | +0 | +1 | +1 |
| 6 | `tool_loop` | **0 个** tool_call（协议失败槽位） | 同上 | +0 | +1 | +1 |
| 7 | `tool_loop` | **>1 个** tool_call（协议失败槽位） | 同上 | +0 | +1 | +1 |
| 8 | `tool_loop` | 响应解析失败 ∧ 重问额度未用尽 | 重问 → `tool_loop` | +0 | +1 | **+0** |
| 9 | `tool_loop` | T1 ∨ T2 ∨ T3 成立 ∨（解析失败且重问已用尽） | `generate`（**携已有结果**） | — | — | — |

**第 3–8 行按事件互斥划分，一次模型响应恰好命中其中一行。** 第 4 行的工具执行失败在本地发生、**不产生额外请求**，因此与第 3 行共用同一次请求计数——这正是早期草案两行重叠的根源。

> **「参数非法也消耗轮次」（第 5 行）是刻意的**：否则模型可靠连续发非法调用把轮次上限架空。

- 达上限未收敛时**携已有结果继续，不因未收敛而拒答**。

### 6.2 工具面（冻结清单）

全部只读、全部经 Repository 层（D7）、参数经严格 Pydantic 校验、**`project_id` 不在任何 schema 里**：

| 工具 | 参数 | 返回 |
|---|---|---|
| `lookup_symbol` | `kind`（**封闭枚举，恰五值**：`class`/`interface`/`enum`/`annotation`/`method`）、`name`（字符串） | 是否存在 + 命中位置列表（`rel_path`、行段、所属包），有上限 |
| `list_annotated` | `annotation`（字符串）、`scope` | 命中符号列表 + 计数 + 扫描范围声明 |
| `count_matching` | `scope`、`pattern_kind`（**封闭枚举，恰三值**：`exact_name` / `name_prefix` / `path_prefix`）、`pattern`（字符串） | 计数 + 扫描范围 + 匹配规则声明 |
| `check_path` | `rel_path`（字符串） | 是否在索引内 + active 状态 + 后缀是否在摄取范围 |

**`scope` 的形态冻结（`PG-P16-04`）**：`scope` 是**相对于语料视图根的 POSIX 目录前缀字符串**，不是枚举。校验规则：非空、不含 `..`、不以 `/` 开头、规范化后必须是当前快照 manifest 中**某条 `rel_path` 的真前缀或等于某个目录层级**；不满足即参数非法（§6.1 第 5 行）。**空 `scope` 表示全快照范围，必须显式写为 `""` 而非省略**。

**`pattern_kind` 的三值一律为确定性字符串匹配**（精确名 / 名前缀 / 路径前缀），**不引入正则**——因此不存在回溯风险，匹配代价与快照条目数线性相关。

**`LLMClient` 的工具调用输入/输出结构（在本规格冻结，不推迟到 packet）**：

- 输入：`complete(*, system, user, json_mode=False, tools: Sequence[ToolSpec] | None = None)`。`tools=None` 时行为与现状**逐字相同**（P0 对照路径与既有四调用点由此不受影响）。
- 输出：`LLMResult` 新增 **`tool_calls: tuple[ToolCall, ...] = ()`**，`ToolCall` 为 `(id: str, name: str, arguments_json: str)` 的严格 Pydantic 模型。**既有 `text`/`model`/`usage` 三字段语义不变**，纯加法。
- `arguments_json` 保持**未解析的原始字符串**——解析与校验在节点层完成（§6.3 末段），使"解析失败"与"参数非法"成为两个可分事件（分别对应 §6.1 第 8 行与第 5 行）。

- **返回结构化事实，不回传文档正文**。正文仍只经 retrieve 与引用校验路径。
- `pattern` 类参数**不得**被当作可执行文本；匹配规则限定为确定性字符串/前缀/枚举匹配，**不引入正则回溯风险**（实现须声明所用匹配算法并有上界）。
- **绝对禁止**（ADR-0011 §3）：任何 shell / 进程执行工具（含 `grep`/`find`/`cat` 的"安全包装"）、任何写工具、任何跨 project 查询、任何返回正文全文的工具、开放式无界 ReAct。
- **工具执行失败**：确定性降级——记 warning、该轮结果标记不可用、按上限判定继续或结束，**不重试、不无界**。工具永不执行被查询内容。

### 6.3 数值上限（全部冻结为常量，实现不得内联魔数）

| 项 | 值 | 越限行为 |
|---|---:|---|
| 一次模型响应携带的 tool_call 数 | **1** | >1 判协议违规，按解析失败处理 |
| 单个字符串参数长度 | **200** 字符 | 参数校验失败，不调用 Repository |
| `scope` 路径前缀长度 | **512** 字符 | 同上 |
| 单次工具返回的 `locations` 条数 | **50** | 截断并置 `truncated=true` + `truncation_reason` |
| 单次工具结果序列化后的 token 上限 | **2000** | 截断并置 `truncated=true`；**截断的结果不得用于否定证明**（§4.4 硬约束 2） |
| 子循环内工具结果累计 token 上限 | **6000** | 达上限即结束子循环 |
| 单次工具执行超时 | **5 s**（本地 DB 只读查询） | 记 warning，结果标不可用，轮次 +1 |

**参数校验在节点层完成，非法参数与非白名单工具名一律不到达 Repository**——D7 的隔离不能靠 Repository 自己兜底。

### 6.4 预算守卫：**四个**计数器（确定性，冻结）

第二轮前审坐实（`PG-P16-04`）：`MAX_LLM_REQUESTS = 6` 是 `src/devkb/agent/state.py` 的**单一全局常量**，被 `nodes.py` 的预算守卫、`graph.py` 与 `evaluation.py` 共用。**若直接把它改成 11，既有 plan/evaluate/refine/generate 四个调用点也会一并拿到 11 的预算**——「既有四调用点逻辑上限仍为 6」在早期草案里**没有任何执行机制**，只是一句愿望。

**冻结四个计数器与四条硬顶**：

| 常量 | 值 | 约束对象 |
|---|---:|---|
| `MAX_NON_TOOL_REQUESTS` | **6** | plan / evaluate / refine / generate 四个既有调用点（含其重问）——**即原 `MAX_LLM_REQUESTS` 的语义，改名不改值** |
| `MAX_TOOL_LOOP_REQUESTS` | **5** | 工具子循环内的全部请求（含其重问） |
| `MAX_TOTAL_REQUESTS` | **11** | 单 run 发往供应商的请求总数 |
| `MAX_TOOL_ROUNDS` | **4** | 工具执行轮次 |

- **既有四调用点的守卫改为检查 `non_tool_requests`，不是 `total`**——这样它们的预算下界与 P0/P1/P1.5 逐字相同，**是机制保证而非算术巧合**。
- **`MAX_LLM_REQUESTS` 原名保留为 `MAX_NON_TOOL_REQUESTS` 的别名或直接改名**，须在 packet 中冻结改名范围，并有回归用例证明既有四调用点行为逐字不变。
- **`generate` 预留规则**：每轮开始前检查 `MAX_TOTAL_REQUESTS − total_requests − 1 ≥ GENERATE_RESERVE`；不成立即结束子循环（T2）。`GENERATE_RESERVE` 为冻结常量，取 **1**；若本 run 已发生过 L0/L1 违规（重生成仍可能触发）则取 **2**。
- **「子循环不侵蚀既有预算」现在是 `non_tool_requests ≤ 6` 这个独立计数器的直接推论**，不再依赖 `11 = 6 + 5` 的算术，也不再依赖任何一处口径没写错。
- 达轮次上限而未收敛时，**携已有结果继续，不因未收敛而拒答**。

### 6.5 计数口径（与 §6.1 状态转移表逐行对应，互斥且穷尽）

| §6.1 行 | 完整事件 | `non_tool` | `tool_loop` | `total` | 轮次 |
|---:|---|---:|---:|---:|---:|
| 3 | 1 个合法 tool_call ∧ 工具执行成功 | +0 | +1 | +1 | +1 |
| 4 | 1 个合法 tool_call ∧ 工具执行失败/超时 | +0 | +1 | +1 | +1 |
| 5 | 1 个 tool_call ∧ 参数非法/非白名单 | +0 | +1 | +1 | +1 |
| 6 | 0 个 tool_call（协议失败槽位） | +0 | +1 | +1 | +1 |
| 7 | >1 个 tool_call（协议失败槽位） | +0 | +1 | +1 | +1 |
| 8 | 解析失败后的重问 | +0 | +1 | +1 | **+0** |
| — | plan / evaluate / refine / generate 的任一次请求（含重问） | **+1** | +0 | +1 | +0 |

- **工具本地执行失败不单独占一行**——它已并入第 4 行的完整事件；本地执行不产生供应商请求，故第 3、4 行的请求计数相同。这消除了早期草案两行可被同一次调用同时命中的歧义。
- **重问计入 `tool_loop` 与 `total`，但不动轮次**——否则"重问"会变成绕过轮次上限的通道。
- 四个计数器**只增不减**，由确定性代码维护，**模型不得覆盖**（D6 原文保留）。

### 6.6 可断言性（本阶段的测试硬要求）

必须能用 FakeLLM 精确断言：节点序列、**每个 run 的供应商请求总数**、**子循环轮次**、每轮请求的工具名与参数、终态。新增的不确定性**只允许**存在于「子循环内每轮选了哪个工具」这一点。

## 7. refine 的符号约束（RT-17）

- refine 改写查询时，其中的**路径 / 符号 / 框架名 / 状态词只能来自**：用户问题原文、已检证据、或 inventory 查询结果。三者之外的符号**不得进入改写后的查询**。
- 模型若写出遍历/执行类动作（`grep`、`find`、`cat` 等），确定性代码**拒绝执行并记 warning**，必要时转为对应的结构化工具调用；**绝不实现 shell 执行**（RT-17 的原判据是「区分检索查询与真实可用的只读工具动作」，不是「把 shell 包一层」）。
- 用户限定的源码范围（如"只看生产实现"）在 refine 后必须保持，不得扩到测试/生成代码。

## 8. 全局否定 / 穷举的确定性证明与 `confirmed_undocumented` 解锁

- **`confirmed_undocumented` 首次可产出**，且**只在有 inventory 支撑时**。每条必须绑定四要素：**commit + 扫描范围（含后缀集合）+ 匹配规则 + 覆盖计数**。缺任一要素即不得产出，退回条件式措辞。
- **这是一次有意的契约变更**：P1.5 对该分类有「永不产出」的单测锁定，本阶段必须**改写那条冻结用例**并在任务清单显式登记为契约变更。**不得静默放开**——改写的用例必须变成「无 inventory 支撑时仍永不产出」的更强断言，而不是删掉。
- **语义证据只负责解释成员**，不负责证明覆盖（RT-21 原判据）。「一共 26 个 endpoint」的数字来自 inventory 计数，不来自模型数数。
- 静态不可见边界（动态注册、反射、注解处理器生成）单独披露，不计入论域。
- **未摄取格式一律不进否定证明的论域**（§4.3）。

## 9. 安全边界与注入风险增量（D8）

- D8 结论「只读工具面消除执行类风险」不变；工具面仍全部只读。
- **新增一条风险，如实声明不宣称消除**：工具返回值进入模型上下文，被检索文档中的指令载荷因此有了一条**新的间接影响路径**（模型可能因文档内容而选择某个工具或参数）。缓解：参数经严格 schema 校验且无自由文本可执行字段；返回结构化事实不含正文；子循环有硬上限，最坏情形是浪费预算而非越权。**写入 README「已知限制」，不得省略。**
- P1.5 的 policy-refusal 终态与三张词法闭表继续有效；**policy 命中时一律不进入工具子循环**。
  **两层的拓扑事实不同，须分开表述**（早期草案把两层都写成「零 LLM 调用」，被 2026-08-10 前置审查判为失实）：

- 日志/轨迹不打印文档正文与 secret（D8 不变）；工具调用轨迹记录工具名、参数与结果摘要，**不记录问题正文以外的自由文本载荷**。

## 12. P1.6 验收标准（退出 Gate）

早期草案的十条里有多条依赖自由文本（「零编造符号」「零不存在断言」「零未经核验符号」）、无确定义（「可用回答」）或无判别力（holdout「跑一次就算」），被 2026-08-10 前置审查判为**重蹈 P1.5 的不可判 Gate**（`PG-P16-06`）。

**本节的可判性来自一处设计红利**：§4.4 规定用户可见文案是 proof 结构的**确定性纯函数渲染**，因此**判据一律定义在结构上，不定义在文本上**——「零不存在断言」不再靠扫描措辞，而是断言「论域外主体的 `verdict` 恒不为 `not_found`」。

**G9 的 token 抽取规则（冻结）**——从 refine 输出中抽取待校验 token，规则为**确定性词法**，与 `src/devkb/agent/evidence_types.py` 的 `iter_path_tokens` / `iter_symbol_tokens` **复用同一实现**（不新建第二套规则，避免两处口径漂移）：

- 路径 token：含 `/` 或以已摄取后缀结尾的连续非空白串；
- 符号 token：首字母大写的驼峰标识符、以及 `Xxx.yyy(` 形态中的方法名；
- 比对集合三者：① 用户问题原文经同一规则抽取的 token；② 本 run 全轮证据的 `rel_path` 与 `title_path` 经同一规则抽取的 token；③ 该快照 inventory 的符号名与路径全集。

### 12.1 判据纪律（自 P1.5 的教训写入，本阶段起生效）

P1.5 的退出 Gate 有两条在实际运行中失去判别力，本阶段起以下三条纪律具约束力：

- **「本轮无样本触发」不得记为通过。** P1.5 的 `zero_full_without_required_evidence = True` 是在 20 题**零 full** 的情况下取得的——一个从未被触发的守卫返回 True，不构成守卫有效的证据。本阶段每条 Gate 必须同时报告**施压样本数**；施压样本数为 0 时一律记为「**未施压**」，既不记通过也不记失败。
- **「判不了」不得记为通过（fail-closed 继续有效）。** 沿用 T31.2R-c 的三态判定：`True` / `False` / `None`，`None` 不计入通过。
- **机器可判定子集全绿 ≠ 判据达成。** P1.5 的 `not_found_decidable_ok = 104/104` 全绿，而人工在同一批数据里找出编造类名。凡判据含**命题级**内容（某物在仓库里存不存在、某断言是否被证据支持），必须显式声明「机器覆盖到哪、剩下的归谁判」，并把未覆盖部分路由到人工复核任务，**不得用可判定子集的绿色代表整条判据**。

**明确不作为 P1.6 出口条件**（属 P1.7/P2）：`.vue/.ts/.sql` 已摄取、检索指标提升、`claims` 与正文一致、在线 L2。**P1.6 通过只证明「仓库级确定性事实可查、可证、可界」，不得对外宣称检索质量或语义正确性有提升。**
