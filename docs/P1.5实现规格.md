# 《P1.5 真实仓库可靠性/诚实加固 实现规格》

> 状态：**草案**（待 ADR-0010 批准后冻结为当前阶段唯一实现依据）
> 前置 Gate：P1 已于 2026-07-22 验收关闭（结论不变）
> 依赖：《ADR-0010》《P1后真实仓库可用性测试问题记录》（RT-01～RT-23）《范围冻结与架构决策》D6/D7《P1实现规格》《Evaluation-v1.5》
> 执行状态见《P1.5任务清单》。

## 1. 目标与范围

P1.5 只做**一件事**：把 P1 已证明的"能安全问答、可回放"提升为"**回答契约诚实且一致**"。它修的是现有能力的正确性，不长新能力。

P1.5 冻结交付（全部在 D6 与现有依赖栈之内）：

1. 用户指定的证据类型/路径成为**硬约束**（RT-01/05）；
2. `not_found` 四分类，P1.5 完整实现其中三类（RT-02/15）；
3. 跨轮证据覆盖单调性与 partial 保留（RT-16/20）；
4. evaluate/generate/finalize 确定性一致性校验（RT-03/08）；
5. partial 认知口径与安全/配置覆盖矩阵（RT-18/19）；
6. 独立 policy-refusal 终态（RT-22）；
7. 拒答/partial 的静态摄取覆盖披露（案例三/十的廉价版）；
8. unknown project 的模型初始化 fail-fast 顺序（RT-23）；
9. 有界的逐候选诊断轨迹（RT-07 最小版）；
10. warning 的 attempt/已解决区分（RT-10）。

**明确不做**（推 P1.6/P2，见 §13）：多语言摄取（`.vue/.ts/.tsx/.sql`）、仓库级 inventory/symbol/annotation、全局否定与穷举的确定性证明、动态工具调用、默认检索机制变更、在线 L2/NLI、LangFuse、MCP、轻量 UI/SSE、云部署。

## 2. 继承与兼容性

- P0/P1 的 `LLMClient`、`Embedder`、Repository/project_id 隔离（D7）、引用路径/行号契约、`fixed-rag` 对照 pipeline 全部保留。
- **D6 边界不变**：仍恰好 plan/evaluate/refine/generate 四个在线调用点、单 run ≤6 供应商请求、控制流由确定性代码判定。P1.5 可扩展这四点的**结构化输出 schema 与 Prompt**，但不新增调用点、不引入工具调用。
- **ADR-0002 embedding 冻结不变**：`Qwen/Qwen3-Embedding-0.6B` 与 `vector(1024)` 不动。
- **默认检索机制（Vector + FTS → RRF + HNSW）不因 P1.5 变更**。RT-06 的召回改进需先做同题对照实验，属 P1.6；P1.5 不得未经实验把 P1 已记录表现较差的方案设为默认。
- P1.5 会使 `PROMPT_VERSION` 递增、P1 的 Prompt 冻结在本阶段失效；这不回改 P1 验收结论，也不重跑或据此调优 P1 holdout。
- CLI 与 `POST /ask`、`GET /runs/{id}`、`GET /healthz` 只增字段、不删除既有字段；Answer/Run JSON 对既有消费者保持后向兼容。

## 3. 先冻结 Evaluation-v1.5（前置纪律）

动任何 `src/`、Prompt 或阈值前，先按《Evaluation-v1.5》完成回归集冻结：18 条 post-P1 复现路径 + 反例（自然问法、合法安全咨询、真正无资料、格式未摄取）+ 每题预登记（必需证据/禁止替代证据/预期 mode/关键符号）+ 分环节统计（retrieval / evidence-selection / claim-support / final-consistency）。不重跑、不据此调优已使用的 P1 holdout；另建 v1.5 dev/holdout。

## 4. 证据类型硬约束与权威性分层（RT-01/05）

- **必需证据模型**：确定性代码从用户问题解析出被明确要求的证据类型/路径（如"生产 Java 实现""数据库迁移""引用某类"），构造 required-evidence 清单；plan/evaluate 的结构化输出增加逐项覆盖状态字段。
- **判定约束**：`full`/`sufficient→full` 要求每个必需证据类型都有**直接匹配引用**；测试、设计文档、历史计划、dev-log 只能作补充，**不得占用或替代必需生产证据**。缺任一必需类型时最高只能 `partial`。
- **权威性分层**：区分 current docs / production source·config / tests / historical plans·audits / dev-log。规划材料只能证明"规划过/范围状态"，不能证明"已实现"。分层可用确定性规则 + Prompt 约束组合；具体权重以 Evaluation-v1.5 结果裁决，不凭少数案例拍定。

## 5. `not_found` 四分类与事实校验（RT-02/15）

- 枚举四类：`missing_from_current_evidence`、`unsupported_or_not_ingested`、`confirmed_undocumented`、`forbidden_or_unavailable_by_policy`。
- **P1.5 完整实现三类**：
  - `missing_from_current_evidence`——本轮证据集未覆盖，可能是召回失败；
  - `unsupported_or_not_ingested`——由语料视图 **manifest** 廉价判定（该后缀不在 `SUPPORTED_SUFFIXES` 或该文件未入库）；
  - `forbidden_or_unavailable_by_policy`——见 §9，不进入普通 `not_found`。
- **`confirmed_undocumented` 与"全库不存在"需确定性 inventory 支撑，属 P1.6**。P1.5 **不得断言全局不存在**；对全局否定/穷举题，降级为诚实的"当前证据不足以穷举确认"能力边界声明（见 §15 第 6 条），既不假拒答、也不假断言不存在。
- **事实校验范围含全部检索轮历史**：不得把出现在任一轮证据路径中的 active 文件写成"不存在"，不得把前轮已支持的方面在后轮凭空升级为缺失。用户问题未给出的路径/类名/字段名/"源码不存在"等强断言，必须来自证据；否则只陈述当前证据不足。

## 6. 跨轮证据覆盖单调性与 partial 保留（RT-16/20）

- 把用户要求拆为**证据方面（aspect）**；跨轮**逐方面保留最佳证据**并记录淘汰原因。最终充分性按单调覆盖矩阵判定，不看最后一轮扁平 top-k。
- 覆盖只能增加；某方面从"已支持"退为"缺失"必须有"原证据被证伪"的理由，仅被新轮挤出不算。
- **只要至少一个用户方面有直接证据，就交付范围准确的 `partial`**；`refusal` 仅用于零可交付证据，且不得因其他方面缺失而清空已支持方面。

## 7. 节点一致性与 finalize 校验（RT-03/08）

- `finalize` 前做**确定性一致性与覆盖差分检查**：`mode`、正文、`claims`、`not_found`、`limitations` 必须相符；正文声称已证明的内容不得同时出现在 `not_found`。
- `finalize` 不得把 evaluator 的 missing 项**无事实校验地**注入用户可见 `not_found`（RT-15 交叉）。
- 第二稿（regen）除重过 L0/L1 外，必须**重做覆盖度与一致性检查**；必要时准确降级，而不是把错误缺口原样交付（RT-08）。

## 8. partial 认知口径、安全与配置覆盖矩阵（RT-18/19）

- `partial` 的正文与总结**限定在已验证的资源/操作**，不得对未覆盖方面给出绝对结论。
- **安全类问题**输出 `resource × operation × enforcement-layer` 覆盖矩阵，明确区分"Repository 语句自身过滤"与"Service 前置校验后调用非 owner-scoped 语句"，不把二者混为统一双重防线。
- **配置类问题**分别验证 `scope / fallback / required·non-empty / length·strength / runtime-validation`；错误消息或文档建议不得冒充代码强制条件（如把 Compose `${VAR:?}` 非空检查表述为 secret 强度保证）。
- 上述矩阵是否为通用契约还是安全/配置专用评审器，以 Evaluation-v1.5 的多方面问题对照裁决。

## 9. policy-refusal 终态（RT-22）

- 对明确索取系统 Prompt、凭据、隐藏文件内容或要求越权执行命令的请求，在**检索潜在敏感语料和调用任何工具之前**识别并返回独立的 `policy_refusal`：固定、不含秘密的文案；不检索、不生成、不执行、不编造。
- 受保护对象（系统 Prompt、密码、API key、`.env` 输出、命令执行结果）**不得写入普通 `not_found`**，不得暗示"检索到就能回答"。
- 用多种攻击改写、合法安全咨询（如"如何保护 API key"）和普通 `.env.example` 文档题验证召回率与误杀率，避免只针对单句写关键词特判。

## 10. 摄取覆盖披露（案例三/十的廉价版）

- `refusal`/`partial` 附带**静态摄取覆盖披露**：说明本项目摄取哪些后缀、不摄取哪些，使"格式未摄取"可与"仓库确实无源码"区分。
- 这是静态能力披露，不做逐题语言/意图推断（那需要更完整的语言与结构支持，属 P1.6）。

## 11. unknown project 的 fail-fast 顺序（RT-23）

- 输入校验与 project 解析必须**先于** `_get_embedder()` / `_get_llm()`。unknown project 在任何模型/client 初始化前返回结构化 404、统一脱敏错误体、零 run/step/tool、零外部调用。
- 新增冷服务 loader spy 回归：unknown project 时两个 factory 调用次数均为 0；现有注入已实例化 Fake 的测试无法覆盖此顺序，须补 spy。

## 12. 诊断轨迹（RT-07 最小版）

- 每轮保存**有界的 per-query 候选元数据**：`chunk_id`、`rel_path`、line range、rank、score、融合/截断原因，使"未召回 / 低排名被截断 / 被融合淘汰 / 已给模型但未采用"可事后区分。
- 每个 refine term 记录来源；finalize 注入的 missing 记录来源与事实校验结果。
- 继续禁止保存文档正文与任何 secret（D8/安全纪律不变）。RT-06 的召回改进、RT-21 的 inventory 属 P1.6，不在本节。

## 13. 明确不做（推 P1.6/P2）

- **P1.6**：`.vue/.ts/.tsx/.sql` 多语言摄取（RT-13）；manifest/symbol/annotation inventory 与精确文件/类/方法/注解查找（RT-21）；全局否定与穷举的确定性证明；path/symbol/method-aware 检索改进（RT-06）；refine 查询漂移的确定性符号约束（RT-17）；**动态工具调用（有界 function-calling 子循环）**及其对 D6 的窄修订。
- **P2**：LangFuse（P2-A）、MCP（P2-B）、在线 L2/NLI、轻量 UI/SSE、云部署、reranker、n8n 等（受 ADR-0009/路线图-v2 后续 Gate 约束）。

## 14. 测试与 Evaluation v1.5

- CI 与测试不得调用真实模型/真实 API（FakeEmbedder/FakeLLM）；业务代码禁止 `if testing` 分支；每项任务完成时 ruff、pyright、pytest 零错误全绿。
- 新增 Evaluation-v1.5 dev 回归门并入 `make eval-ci`；P0/P1 兼容回归继续全绿；L0/L1 继续全绿。
- warning 区分 `resolved_warnings` 与 final active warnings，并带 node/attempt（RT-10）。
- 不引入在线 NLI；claim-support 语义校验建立**离线/人工 L2 回归包**，不进在线路径（D9 不变）。

## 15. P1.5 验收标准（退出 Gate）

以下全部满足才可勾选 P1.5 完成：

1. Evaluation-v1.5 的 18 条固定复现全部达到各自新预期。
2. 不再把 active/indexed 文件断言为不存在；`missing/not_found` 中不出现未经证据支持的路径/类名/字段。
3. 用户明确要求的证据类型未满足时，**绝不判 `full`**；测试/设计/dev-log 不得替代必需生产证据。
4. `mode`、正文、`claims`、`not_found`、`limitations` 一致；至少一个方面有直接证据时交付范围准确的 `partial`，不整体清空。
5. Prompt Injection/秘密提取/越权命令请求进入独立 `policy_refusal`，无泄露、无执行、无敏感检索；合法安全咨询反例不被误杀。
6. 全局否定/穷举题给出诚实**能力边界声明**（不假拒答、不假断言"不存在"）；真正的穷举/否定**证明**能力属 P1.6，不在本 Gate。
7. 格式未摄取导致的缺失被标为 `unsupported_or_not_ingested` 并附覆盖披露，而非"仓库无源码"。
8. unknown project 在加载 embedder/LLM 前 fail-fast 404，loader spy 证明两个 factory 均 0 次，且保持零持久化/脱敏错误体。
9. 新 v1.5 holdout 只运行一次并留档；不据结果回改 Prompt/阈值/权重/标注。
10. P0/P1 兼容回归 + 本地 `make ci && make eval-ci` + 当前头提交 GitHub Actions 全绿；`PROMPT_VERSION` 递增已记录。

**明确不作为 P1.5 出口条件**（均属 P1.6）：Controller 穷举得到 6 类/26 endpoint、`.vue/.ts/.sql` 已摄取、动态工具调用可用。P1.5 通过只证明"回答契约诚实且一致"，不得对外宣称已具备仓库级审计或工具调用能力。
